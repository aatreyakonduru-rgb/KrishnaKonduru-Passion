What Mētis 2.0.0 is and the approach it is built on.

Goal

Mētis 2.0.0 is a shared knowledge service for many teams. Each team builds and owns its own knowledge base (KB), ontology, knowledge graph and impact matrix. Only that team can change its KB; every other team can read it. People manage, check and fine tune their KB in a web UI, ask questions in plain English, and the answers and their feedback make the KB better over time. A named person approves every change that matters.

What we are building

No single public approach covers all of this, so Mētis 2.0.0 is built as a mix, called the evidence graph:

  1. Build the graph of tables, columns, endpoints, screens, jobs and code from parsers and database catalogues, not from an AI's reading. This gives complete and exact impact analysis.
  2. Have the AI write the readable pages on top of that graph, with a checked source on every line (the rule Mētis already follows).
  3. Answer questions with a mix of keyword search, meaning search and walking the graph, plus summaries of each area for big-picture questions (the GraphRAG idea).
  4. Keep every fact with the commit or snapshot it came from, so the KB can update itself when code changes and show what moved.
  5. Publish each team's KB as a Google OKF v0.2 bundle (Markdown with YAML frontmatter in Git), with Mētis source tags in OKF's source and trust fields.

Fourteen ways to build and organise knowledge and context for AI, each with what it is good and weak at.

1. Plain vector search (classic RAG)

Split documents into chunks, turn each chunk into a vector, and at question time fetch the closest chunks and give them to the AI.

Good at: Quick to set up; good for "where is X explained".

Weak at: Misses links that span files; weak on "what breaks if"; chunks lose their context; answers hard to trace to one line.

2. Hybrid search with context added to each chunk

Keyword search (BM25) and vector search together, a re-ranker on top, and each chunk stored with a short note on which document and section it came from (Anthropic calls this contextual retrieval).

Good at: Better hit rate than plain vectors; exact names like table and column names are found by keyword.

Weak at: Still finds passages, not relationships; impact questions need more.

3. Summary tree (RAPTOR)

Group chunks, summarise each group, then summarise the summaries, building a tree; search all levels.

Good at: Good for big-picture questions about a module or a system.

Weak at: Summaries are AI-written, so they need their own source checks; rebuild cost when content changes.

4. AI-extracted knowledge graph (Microsoft GraphRAG)

An AI reads the text and pulls out entities and relations, groups them into communities and writes a summary per community. Local questions walk the graph; global questions use the community summaries.

Good at: Strong on themes across a whole body of text; shows connections people did not write down.

Weak at: Costly to build; the AI can invent or miss relations, so the graph is not complete enough on its own for impact analysis. The repository says it is largely in maintenance mode (checked 13 Nov 2026).

5. Lighter graph retrieval (LightRAG, HippoRAG)

Smaller graph built during indexing, used to steer retrieval: LightRAG mixes graph and vector search at two levels; HippoRAG ranks passages by walking the graph from the question's entities.

Good at: Cheaper than full GraphRAG; handles questions that need two or three hops.

Weak at: Same trust problem as any AI-extracted graph; younger projects. Default stores are in-memory and the server ships with authentication off (checked 13 Nov 2026).

6. Parser-built code and data graph

Read code and SQL with parsers (for example tree-sitter, SCIP code indexes, SQL parsers such as sqlglot) and database catalogues, and record exact links: this endpoint reads that table, this job writes that column.

Good at: Complete and exact for what the parsers cover; repeatable; no AI guessing; best base for impact analysis.

Weak at: Needs a parser per language or format; misses meaning that only lives in people's heads or in Confluence.

7. Ontology first, semantic layer

Agree the business and technical terms and how they relate (member, provider, measure, table, screen) before filling them in; a semantic layer maps business terms to tables and columns (the dbt semantic layer and Snowflake semantic views work this way).

Good at: Shared language across teams; answers use the business's words; joins between teams' KBs become possible.

Weak at: Needs an owner and upkeep; slow if done too formally.

8. Data lineage and catalogue standards (OpenLineage, DataHub, OpenMetadata)

Jobs report what they read and wrote in a standard event format; a catalogue stores datasets, owners and lineage.

Good at: Standard format; owners and lineage in one place; lineage from real runs, not only code.

Weak at: Needs the jobs to report events or a connector per tool; another system to run.

9. Time-aware knowledge graph (Graphiti / Zep)

Every fact has a valid-from and valid-to; new information closes old facts instead of overwriting them.

Good at: The KB can update itself and still show what was true before; good for "what changed since".

Weak at: More complex storage and queries; mostly used for agent memory today. Needs a graph database and an LLM key; its reference servers have no authentication (checked 13 Nov 2026).

10. Just-in-time agent search

No index: an agent searches the repos live (grep, file reads, long context) for each question.

Good at: Always current; nothing to build.

Weak at: Slow and costly per question; results vary between runs; nothing to review or approve; no cross-team view.

11. AI-written wiki (DeepWiki, Devin wiki)

An AI writes a page per module or repo from the code, with diagrams.

Good at: Readable quickly; good for onboarding.

Weak at: Pages can state things the code does not show unless every line is checked; hard to query for impact.

12. Evidence-first KB (as in Mētis 1.2.5, kept)

Prompts write the KB; every line carries a source tag checked by a tool; anything without a source becomes a question for a named role; links only from sourced lines.

Good at: Highest trust; reviewable; fits the no-guessing rule.

Weak at: Full builds are heavy; graph depends on what the prompts write; no learning loop yet.

13. Four-layer knowledge architecture on open standards

Split the knowledge into four layers that are kept apart: the ontology (types, allowed links, rules: OWL, RDFS, SKOS, SHACL), the knowledge graph or matrix (the real things and their links: RDF and SPARQL, or a property graph with GQL), the semantic or metrics layer (business terms, KPI formulas, data views: YAML or SQL semantic specs, DCAT) and the context layer (where each fact came from, events, permissions, decisions: W3C PROV, OpenTelemetry, JSON-LD).

Good at: Business rules stay out of app code and AI prompts; open standards mean other tools can read the KB; each layer can change on its own; provenance is a standard, not a custom tag.

Weak at: An architecture, not a way to fill the KB: it still needs one of the other approaches (6, 7, 12) to produce the facts; full OWL reasoning and RDF stores add skills and systems to run.

14. Google Open Knowledge Format (OKF) bundle

An open, vendor-neutral format from the Google Cloud Data Cloud team for the AI-written wiki pattern. A bundle is a folder of plain Markdown files, one concept per file (a table, metric, runbook or policy), each with YAML frontmatter (only type is required) and a free Markdown body. Each folder has an index.md so an agent can browse step by step; files link with relative Markdown links, which makes the folder a graph. v0.2 adds optional source lists with per-claim footnotes, a verified-by-a-person flag, a draft, stable or deprecated status with a separate stale_after date, and proof that a metric used an approved formula.

Good at: Plain text, Git-native, no SDK or database; any agent, Obsidian or a static page can read it; tools can rewrite the frontmatter while hand-written bodies stay; very close to how Mētis already writes its KB.

Weak at: A format, not a way to find the facts: links are only as complete as whatever writes them; plain Markdown links have no typed relation or per-link source, so exact impact walks still need a link graph beside it; young spec (v0.2).

Which one is best

For impact analysis and trust, the parser-built graph (6) is the only base that is complete and exact for what it covers. Ontology first (7) is what lets many teams' graphs join up. The evidence rule (12) keeps the readable pages honest. The four-layer model (13) is how the result is organised and which open standards it uses. OKF (14) is the format each team's KB is stored and published in, so any team or agent can read it without Mētis code. GraphRAG-style area summaries (4) and hybrid search (2) are added only for answering questions, and the time-aware facts (9) let the KB update itself.

What not to do

  • Do not let an AI-extracted graph (4, 5) feed the impact matrix directly: a missed link means a missed impact.
  • Do not use just-in-time search (10) as the KB: answers can't be reviewed or approved and vary from run to run.
  • Do not publish AI-written pages (11) without the source check.

Why layers matter for Mētis

  • Business rules live in the ontology and semantic layer, not in prompts or app code, so changing a rule does not mean changing a prompt.
  • The graph can be rebuilt from sources at any time; the ontology and metrics are owned and approved by people.
  • Provenance in a standard form (PROV) means every answer can be traced to source, build and approver.
  • A standard export (JSON-LD, RDF, DCAT) lets other teams and tools read a team's KB without Mētis code.

Reference vocabularies to reuse

  • gist (small business upper ontology: agreements, accounts, organisations, events). A candidate base for the shared core ontology, so teams don't invent core concepts.
  • BFO (ISO/IEC 21838 upper ontology). Strict and academic; likely more than Mētis needs.

Decision rule applied to Mētis

The source text gives two stacks: RDF + SHACL + SKOS + JSON-LD for integration, compliance and AI grounding; GQL property graph + JSON-LD for fast walks where links carry properties. Mētis needs both: cross-team integration and audit, and impact walks where every link carries its source and commit.

  • Inside each team: a property graph (nodes and links with source, commit, owner), walked for impact analysis.
  • Between teams and for audit: export to RDF and JSON-LD, check with SHACL, glossary in SKOS, provenance in PROV, datasets in DCAT.
  • OWL kept light (RL or EL profile); no inferred link is used for impact without a source.
  • Which developers will maintain it (SQL and JSON, or semantic web) is a question for the team; the plan assumes SQL and JSON.

Google's Open Knowledge Format (OKF): what it is, how close Mētis already is, and where it fits in 2.0.0.

What OKF is

  • An open, vendor-neutral spec from the Google Cloud Data Cloud team (June 2026); v0.2 came in July 2026.
  • It writes down the AI-wiki pattern: knowledge as plain Markdown files with YAML frontmatter, so agents and people can browse a knowledge graph without an SDK or database.
  • A bundle is a folder tree. One concept per file (table, metric, runbook, policy, decision); the file's path is its ID.
  • Each folder has an index.md listing what is in it, so an agent loads only what it needs. An optional log.md records changes.
  • Files link with relative Markdown links, for example [customers](/tables/customers.md), which turns the folder into a graph.
  • Frontmatter: type is the only required field; recommended are title, description, resource, tags and timestamp. Readers must keep unknown keys.
  • Tools rewrite the frontmatter and leave the body alone, so generated metadata and hand-written know-how live in one file.

What v0.2 added

  • Provenance: the sources a concept came from (sources[]), with per-claim Markdown footnotes.
  • Trust: tells unverified AI writing apart from facts a person verified.
  • Freshness: status draft, stable or deprecated, plus a stale_after date.
  • Attested computation: a metric can carry proof it was calculated with an approved formula or pipeline.

Where it sits: RAG finds the right entry points in a big bundle, then the agent follows OKF links. MCP gives agents tools and Skills give steps; OKF gives meaning and shared context.

Recommendation

  • Publish each team's KB as an OKF v0.2 bundle. This is recommended as the export; whether it is also the store is still a decision (see Decisions). It matches Mētis's Markdown-in-Git design and the evidence rule (sources, verified, stale) almost one for one.
  • Keep the parser-built typed link graph beside it. Plain Markdown links don't say reads or writes and don't carry a source per link, and impact analysis needs both.
  • Cross-team reading becomes simple: any team, agent or tool reads another team's bundle with no Mētis code.
  • Confirmed in the spec on 13 Nov 2026: Apache-2.0; the only required key is type; sources and trust fields exist. Not in the spec: cross-bundle links, a per-claim quote, a formal validator or schema, a sensitivity tier.

The evidence graph: how the recommended approach works, layer by layer.

1
Sources (read only)
Team repos, database catalogues for every environment, Confluence pages, Jira stories, uploaded documents, answers people gave.
2
Exact facts (graph layer)
Parsers and catalogue queries record nodes and links: table, column, endpoint, screen, job, file, story. Each carries its source and the commit or snapshot it came from.
3
Meaning (ontology and semantic layers)
The shared core ontology plus the team's own terms. Business terms and KPI formulas map to tables and columns. AI suggests terms and links; a person confirms before they count.
4
Readable KB
AI-written pages (BRD, FRD, TRD, manuals, runbooks, data contracts) built from the facts and documents, every line source-checked. Area summaries for big-picture questions.
5
Search and answers
Keyword plus meaning search over pages and chunks with their context, and graph walks for "what uses" and "what breaks". Every answer line cites the KB and is checked.
6
Learning
Ratings, corrections and new questions become proposed KB changes or VALIDATE questions; approved ones become facts and golden questions for testing.
7
Context (provenance, events, permissions)
Runs alongside every layer: each fact keeps its source, build run and approver (W3C PROV); each team's KB is stored and published as a Google OKF v0.2 bundle that any team or agent can read.

Why this mix

  • Impact analysis comes from graph walks over exact links, so it is complete for what the parsers cover and every step shows its source.
  • The AI does what it is good at: writing, summarising and suggesting. A person confirms its suggestions before they become facts.
  • Teams join up through the shared ontology and shared names (database.schema.table, endpoint path), not through guesswork.
  • Each fact knows which commit it came from, so a code change rebuilds only what it touched and shows what changed.

Questions it answers

  • Which screens, endpoints and jobs use table X, across every team?
  • What changes if column Y is dropped or renamed, step by step, with sources?
  • Which team owns the job that loads table Z, and who do I ask?
  • Explain module M to a new developer in business terms.
  • What changed in the KB since the last release?

Three end-to-end ways to build Mētis 2.0.0. Blueprint A is the one we are building.

A. Git-based team KBs with a shared read index

Each team's KB lives in its own repo (or its own folder with code owners). A shared indexer reads every team's published KB on merge and builds one read-only search and graph index. The UI reads the index and opens pull requests for changes.

For: Closest to 1.2.5; Bitbucket permissions already give team write and org read; every change is a reviewed pull request; no new database to run.

Against: Live editing in the UI is slower (each change is a PR); the index needs a place to run and refresh.

B. Central knowledge service

One service with a graph store and a search store; each team has its own space; write access from the team's AD group, read for everyone. Git keeps an export of every published version for audit.

For: Best UI experience: live edits, instant impact across teams, one place to search.

Against: A new service to host, secure and support inside the Elevance network; needs an owner team; access rules live in the service, not only in Bitbucket.

C. Snowflake-based

KB facts and the graph live as tables in a schema per team; Snowflake roles give team write and org read; search through Snowflake's search features; a UI on top (for example Streamlit in Snowflake).

For: Data teams already use Snowflake; roles and audit come with it; catalogue facts are already there.

Against: Depends on which Snowflake features are enabled at Elevance (to confirm); graph walks in SQL are harder; code-heavy teams may not have Snowflake access.

How it is enforced

  • Write rights come from Bitbucket repo permissions and branch protection (blueprint A) or AD groups (blueprint B), never from Mētis settings alone.
  • Every published change is a pull request into the team's KB, approved by the team's KB owner.
  • The shared indexer reads only the published (merged) version of each team's KB.
  • Suggestions from other teams land in the owning team's review queue; they never write directly.
  • No PHI or PII in any KB: masked samples, counts and field names only (current Mētis rule).

Shared core ontology and team terms

  • Core types every team uses: system, module, screen, endpoint, job, table, column, file, story, business term, person-role.
  • Core links: reads, writes, calls, shows, loads, owns, defined-by, tested-by.
  • Each team adds its own business terms under a team namespace; the steward can promote a widely used term into the core.
  • Every node has a global name: team, type and name, for example a table as database.schema.table.

Cross-team links

  • When team A's job writes a table and team B's screen reads the same database.schema.table, the index joins them into one chain.
  • Endpoint calls join on the endpoint path and the service that hosts it.
  • A link that depends on a name match only, with no source on both sides, is shown as "possible" and goes to both teams' queues to confirm.
  • Impact analysis lists the other teams affected and their owners, so a change in one team warns the others.

How questions and feedback make the KB better, and where people step in.

1
Ask
A person asks a question in the UI.
2
Find
Keyword, meaning and graph search over every team's published KB.
3
Answer
The AI answers from what was found; every line cites the KB.
4
Check
A tool checks each citation; lines that fail are removed and the gap shown as "not in the KB".
5
Thumbs up or down
Under every answer. Thumbs up is recorded as a good answer. Thumbs down opens a box where the person corrects the answer or an assumption Mētis made, and can add where the right fact comes from. The reason is logged and shown to leads on a Feedback screen.
6
Suggestion
The correction becomes a suggestion on the Mētis dashboard for the owning team's KB owner: question, answer, correction, and the KB lines it would change. Its source is "answer from person X" plus any document or code line they gave.
7
Owner validates
The KB owner agrees, edits or rejects (with a reason the user sees). Nothing goes into the KB without this step.
8
Update
If the owner agrees, the change is written into the KB and published with the next build; the question and its corrected answer join the golden question set.
9
Test
Every build re-asks the golden questions; if answers get worse, publish waits for a person.

Self-updating from sources

  • A merged code change triggers a rebuild of only the facts and pages that came from the changed files.
  • Database catalogue snapshots are compared per environment; drift becomes a change for review.
  • Facts that no longer have a source are closed (kept in history), not silently deleted.
  • Pages whose sources changed are marked stale until rebuilt.

What fine tuning means here

  • No model training. The KB, the terms, the synonyms and the golden questions are what get tuned.
  • Corrections improve the KB itself, so every later answer benefits, for every team that reads it.
  • Answer style settings per team (short or detailed, business or technical words).

Role leakage

  • A build run by a person with a privileged role writes what that role can see into a repo the whole team reads.
  • Low in D01 and T01 where data is desensitised. Real wherever unmasked values exist, such as prod.
  • Keep Snowflake evidence to schema (names, types, policy names), not row values. Tag every file with environment and role. Make a pattern scan mandatory for prod.

Devin facts checked on 13 Nov 2026

  • API v3 creates sessions at /v3/organizations/{org_id}/sessions. Service user keys suit shared tools; personal tokens act as the person and are off by default on Enterprise.
  • Automations can start a session on a schedule, with an ACU limit per session and a run limit per time window (new automations default to 50 runs per hour).
  • Outposts keep command execution on your machines but the agent loop runs in Devin's cloud. Not confirmed available for your account type.
  • Dynamic Workflows are off by default for Enterprise accounts until an admin turns them on.

Mētis scans the environment it runs in and shows what it found in Settings: repositories, service accounts, MCP servers and secret names. A lead saves the result as the expected setup, and every later scan is compared with it.

What 'local environment' means here

  • Mētis is installed as a plugin into a Devin session, and that machine is disposable. The scan therefore reads what the session can see: its Devin organisation, its checkout, its environment variables and its Devin configuration files.
  • It is a snapshot taken on each run. The result is written to the KB repo (for example .metis/detected-setup.yaml) so it survives the session.
  • It is the same idea as a pre-flight check: a refresh that would fail on an expired Confluence token stops before it spends compute.

What the screen shows

  • One row per item: detected, expected, status (match, extra, missing, fails, not testable).
  • 'Save as expected setup' is a lead action. It is logged like an approval and written to the KB repo.
  • Home shows a banner when the last scan differs from the expected setup. A refresh refuses to start on a failed check for a source it needs.
  • Per APM: each team sees its own organisation only.

What it must never do

  • Store or print a token value, password or cookie. Only names, hosts, access level and the result of each check are kept.
  • Read Snowflake rows. Schema names only, as set for the rest of Mētis.
  • Run unattended with a personal token. Use a service user.
  • Change anything. Every call is a read.

Risks and open points

  • Calling the Devin API from a session needs a credential in that session. The secrets list needs ManageOrgSecrets, which is far more than a scan needs. Give the scan its own service user with the narrowest role, or skip the Devin API calls and rely on repo and secret names found inside the session.
  • Whether a session can read the organisation's MCP list is not confirmed. Plan for a manual entry for those items.
  • A saved file listing service account names and hosts is internal information. It holds no PHI or PII, but a lead should approve it before it is committed to a repo the whole team reads.
  • Detected is not the same as allowed. A secret that is present does not prove the account has the right access, so each system gets a read call and, where it makes sense, a write check on the KB repo only.
