# Skill: Onboarding Guide — Role-Specific Learning Guide

You are a **Senior Business Analyst** producing an onboarding guide for a new
team member joining the Acme Claims product team. The guide should give them a
structured, friendly introduction to the platform and their role — covering
what they need to know in their first two weeks.

Different roles need different things:
- **BSA**: domain knowledge, SDLC process, how to use the agentic tools
- **PO**: business capabilities, story review, how to approve gates
- **finance-user**: what the system does for finance, configuration concepts
- **developer**: coming soon (technical onboarding — defer to /investigate and TRD docs)

---

### Role-Specific Content

#### For BSA:

**Your Role:**
- You are the bridge between business stakeholders and the development team
- You own the requirement spec (REQ-{id}-SPEC.md) — you write it, clarify it, approve it
- You approve the intake gate (SDLC_01) and gap analysis gate (SDLC_02)
- You make sure that what gets built matches what the business asked for

**Key Tools for BSAs:**

| Tool | When to Use | How |
|---|---|---|
| `/intake` | After a stakeholder meeting with rough notes | /intake notes "paste your notes" |
| `/dashboard` | Every morning — check what needs your attention | /dashboard |
| `/feasibility-check` | Before committing to intake for a new idea | /feasibility-check "describe the idea" |
| `/intake` | When a Jira ticket arrives with minimal detail | /intake ACME-1234 |
| `/po-story-review` | Before PO creates Jira tickets | /po-story-review REQ-TIN-001 |
| `/explain-capability` | To answer a stakeholder's question about the system | /explain-capability "question" |
| `/intake` | To formally start a requirement | /intake "requirement statement" |

**Your SDLC Gate Responsibilities:** Follow
`.devin/rules/gate-presentation.md` for what is shown before approval and how
your real signer identity is recorded.

| Gate | What You Review | How to Approve |
|---|---|---|
| SDLC_01 | The intake spec — does it capture the business need? | Choose Approve, Reject with reasons, or Approve with notes in the session |
| SDLC_02 | The gap analysis — does the technical scope make sense? | Choose an explicit gate option in the session |

**Worked Example:**
1. You've just left a finance meeting where they described a new PMC cap idea
2. Run `/intake notes "Finance wants PMC capped at LOB level, Medicare only, effective Q2"`
3. Review the draft spec the AI produces — answer its clarifying questions
4. Once the spec looks right: type YES to save it
5. Run `/intake REQ-LOB-001` to start the formal SDLC pipeline
6. Review the intake report and approve gate SDLC_01

#### For PO:

**Your Role:**
- You own the product vision and backlog priority
- You define acceptance criteria — the business tests that confirm delivery is complete
- You approve the story backlog (SDLC_03) — these become Jira tickets
- You do NOT create Jira tickets — you create them manually after approving the stories

**Key Tools for POs:**

| Tool | When to Use | How |
|---|---|---|
| `/dashboard` | Every morning standup prep | /dashboard |
| `/feasibility-check` | When a new idea comes up in a stakeholder meeting | /feasibility-check "idea" |
| `/po-story-review` | Before creating Jira tickets | /po-story-review REQ-001 |
| `/release-notes` | After each sprint — for stakeholder comms | /release-notes REQ-001 REQ-002 |
| `/sprint-review-summary` | Before sprint review meeting | /sprint-review-summary REQ-001 REQ-002 |
| `/pi-plan` | Before PI Planning quarterly event | /pi-plan "REQ-001 REQ-002 new idea" |
| `/what-if` | When stakeholders propose a business rule change | /what-if "describe the change" |

**Your SDLC Gate Responsibilities:** Follow
`.devin/rules/gate-presentation.md` for what is shown before approval and how
your real signer identity is recorded.

| Gate | What You Review | How to Approve |
|---|---|---|
| SDLC_02b | Story candidates — do these cover the business need? | Choose an explicit gate option in the session |
| SDLC_03 | Final story backlog — ready to create Jira tickets? | Choose an explicit gate option in the session |

**Worked Example:**
1. It's Monday morning — run `/dashboard` to see what needs your attention
2. You see REQ-PMC-002 is waiting for your SDLC_03 approval
3. Run `/po-story-review REQ-PMC-002` to check business coverage
4. Review the coverage report — all ACs are covered, no gaps
5. Open the REQ-PMC-002 session and choose an explicit gate option after
   reviewing the artifacts
6. Manually create the Jira tickets using the approved JIRA-BACKLOG.yaml

## STEP 4 — Write the Guide to File

Write the completed guide to:
```
docs/knowledge-base/REPORTS/onboarding/ONBOARDING-{ROLE}-{YYYY-MM-DD}.md
```

Then rebuild the page Argus menu opens, and commit it with the guide:
```
python3 sdlc/framework/tools/gen_reference_pages.py
python3 sdlc/framework/tools/kb_manifest.py generate
```
`sdlc/framework/reference/ONBOARDING.html` shows the newest guide per role, so nobody has to
run this skill to read one. Use `BSA`, `PO`, `finance-user` or `developer` for `{ROLE}` so the page finds it.
The page's first tab, *Getting access*, comes from `ONBOARDING-access-<date>.md`, which is written by hand
from the team's access sheet. This skill does not write or overwrite it.

Tell the user:
```
Onboarding guide written for role: {ROLE}
File: docs/knowledge-base/REPORTS/onboarding/ONBOARDING-{ROLE}-{date}.md

Suggested next steps for your new team member:
1. Read this guide (30 min)
2. Run /explain-capability "what does Acme Claims do?" to explore the system
3. Shadow a /dashboard session or /po-story-review with a senior team member
```

## HARD RULES

- NEVER include technical file names, table names, or code in the guide
- NEVER fabricate capabilities not found in the KB documents
- Guide must be readable in 30 minutes — keep it focused, not exhaustive
- Cite KB documents for all capability descriptions
- If KB is stale: note it — do not present stale information as current
