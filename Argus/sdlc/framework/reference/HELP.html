Everything this framework can do, in one place. Type /help in any session to get a short version of this list; type /help <topic> (for example /help bsa, /help sdlc, /help db) for one section.

  • Skills are slash commands you type in a session — 127 of them, listed below. /catalogue skills prints the whole list from the repository itself.
  • Playbooks are the same capabilities registered in Devin Cloud, each with a !pb_.. macro, so you can start a fresh session already loaded with the instructions. /catalogue playbooks lists them.
  • Agents are role profiles (BSA, PO planner, discoverer, documenter, DB analyst, ETL specialist, validator, migration analyst) that the stage skills adopt; you do not invoke them directly. /catalogue agents lists them.
  • Gates are human approvals. Anything that changes code or ships stops and waits for a named person.

This manual is the one place to read about the framework. The Help page in Argus is built from it, and the Confluence page "Argus User Manual" is its published copy. Argus guide and the guide for Product Owners, BSAs and Scrum Masters are its last two chapters.

Hotfix fast lane

A production incident (a Defect whose summary ends "- PROD" and that has an incident-INC label) can go through one Tech Lead gate, HOTFIX_PLAN_CODE_APPROVAL, in place of SDLC_04 and SDLC_05: the routing and the code are read and approved together, within 4 hours. The independent verifier always runs for a hotfix, whatever the risk tier. Once approved, Devin raises a follow-up review sub-task, due in 2 working days, so the full review still happens (tools/hotfix.py). QA sign-off, release and KB refresh are the same as for any story.

The question comes at the start. When /sdlc or Argus's Start SDLC begins on a Jira key, Devin runs hotfix.py check first. If the ticket passes, it asks: "This is a production incident. Use the hotfix lane?" Yes takes the one Tech Lead gate; no keeps the normal gates. If the ticket doesn't pass and you say it is a hotfix, Devin says what is missing (for example the incident-INC label) and the normal gates run. Nothing else skips a gate.

Cost per story

The Scrum Master and delivery lead dashboards have a Cost tab for the active sprint. For each story it shows the story points, the hours logged on the story and its sub-tasks in Jira, how many of those were on AI-Used sub-tasks, and hours per point. A money figure appears only when the delivery lead sets cost.hourly_rate in .devin/rules/scrum-master-metrics.yaml; until then the tab shows hours. Stories with no time logged are counted separately, because their cost is not known.

The Cost tab also has Devin sessions per story and stage: the team's Devin Cloud sessions grouped by the story key in their title and by stage (intake to KB refresh, plus the independent verifier's extra session), with the number of sessions and their hours (tools/devin_usage.py). The Devin API does not report ACUs per session, so no ACU figure is shown. cost.devin_usage_export in .devin/rules/scrum-master-metrics.yaml can name a CSV from Devin's usage page (session_id, acus) to add them.

Before the sprint closes, /sprint-close-check and the Sprint close tab on the Scrum Master dashboard list every story and sub-task in the active sprint that is not ready. A story needs all its sub-tasks closed, time logged on its sub-tasks, AI-Used or AI-NA, an original estimate and status Ready for Approval or done. A sub-task needs hours logged, the AI label, an original estimate and the same statuses. Each row names the ticket, its story, the owner and everything missing. It only reads Jira. Accessibility and performance checks

/eval opens each page the story changes in Chrome on the Devin machine and checks it (tools/a11y_perf.py). For accessibility it looks for images with no alt text, form fields with no label, buttons and links with no name, a missing page language (these fail the check), and heading jumps, duplicate ids and a missing title (listed as warnings). How to Paste a Playbook into Devin Cloud

  1. Open app.devin.ai
  2. Go to Settings → Playbooks (or your team's Playbooks section)
  3. Click + New Playbook
  4. Fill in:
  5. Title field: copy the text under ## Title in the playbook file
  6. Description field: copy the text under ## Description
  7. Instructions / Body field: copy everything under ## Playbook Body
  8. Save

The playbook will then be available to all Devin Cloud sessions in your account.

Note: Do not paste the file's header metadata (Playbook ID, "Paste into", "CLI equivalent" lines) into the Devin Cloud UI — those are documentation for you. Only paste the Title, Description, and Body sections.

Playbooks vs CLI Skills — Which to Use When?

Use Devin Cloud Playbooks when:

  • You want the entire team to have access without repo setup
  • You are working in a Devin Cloud session (not your local terminal)
  • You want to leverage Devin Cloud Secrets and Knowledge features
  • You want account-wide governance (one place to update, everyone gets it)

Use Devin CLI Skills when:

  • You are working locally in your IDE (Windsurf / VS Code with Devin CLI)
  • You want project-level skills committed in version control
  • You want the skill to trigger automatically from the model without user invocation
  • You want hooks to run alongside the skill

Use both together when:

  • You start a requirement in a Cloud session, then continue implementation locally
  • You want the Cloud playbook for research/backlog and the CLI skills for code generation
  • Both read/write to the same framework/context/session/{OWNER}/{REQ_ID}/ directory, so handoff is seamless

/argus starts Argus (/console is its older name and still works), a web page for the same work you do in chat. Every menu item opens in its own browser tab, and what happens depends on the kind of item.

Pages that are already written. Help, Catalogue, Onboarding guide and Presentation open straight away and do not start a Devin session. They are built from files in the repository (this manual, CATALOGUE.md, the onboarding guides and ARCHITECTURE.html) and checked into sdlc/framework/reference/. When a source file changes, tools/gen_reference_pages.py rebuilds them in the same pull request; the framework check fails if someone forgets.

Onboarding guides. There is one guide per role (BSA, PO, finance user, developer), stored in the knowledge base as ONBOARDING-<role>-<date>.md. The Onboarding page shows the newest one for each role. /onboarding-guide <role> rewrites one, which is worth doing when the knowledge base changes (/kb-refresh after a release), not every time someone wants to read it.

Who is on the roster. Roster check first opens a page listing everyone on the roster, grouped by job role: name, Jira user, the other hats they wear, which gates they can sign, sprint time, who covers for them when they are away, and whether Devin already knows their Devin user id. Its button runs /roster-check for the drift check against Jira. The page only reads the roster; changes still go through the Confluence roster page and a reviewed pull request.

Forms. Settle open questions opens the knowledge-base question form. Devin only starts when you press Send my answers.

Work. Everything else starts one Devin session and opens its result page: what Devin said, the documents it produced (Markdown opens as a formatted page, with a download of the original), questions for you, any gate waiting on your sign-off, and a reply box. Skills that only read run for real; skills that can write start as a dry run with a "Run it for real" button. If you ask for the same thing within 24 hours you get the earlier answer back, with "Run again now" if you want a fresh one.

Sessions close when they are done. A menu item's session is closed as soon as Devin has posted its finished line and is not waiting on a question or a sign-off. The answer stays on the result page, marked "finished · session closed", with Run again instead of a reply box. SDLC pipeline runs are never closed automatically, because they stop at gates for days. You can also close any run yourself with Close session on its result page. Closing a chat closes its card only: your Argus assistant session for the day keeps running for your other requests.

Close versus archive. Close ends the Devin session for good: it stops using resources and cannot be woken again, though its transcript can still be read in Devin. Archive only hides a session from the lists, and it can still be resumed. Argus closes; it does not archive.

My sessions on the dashboard. The dashboard's Sessions tab lists your open Devin sessions, most urgent first. Tick the ones you are finished with and press Close sessions. When Argus opened the dashboard it closes them directly; otherwise the button gives you a block to paste into chat, and Devin closes them there (never the session you are talking to). Closed sessions drop off the list.

Roadmap and Ontology on the Tech Lead dashboard. Both tabs carry a page the knowledge base already has and open it in a new browser tab: Roadmap is the delivery roadmap /roadmap last wrote, Ontology is the Acme Claims ontology. Column details in the ontology that the production documents do not cover come from SIT (T01), and say so.

Independent verifier and Change confidence. A story whose estimation_basis scores RISK=1/2 (medium) or RISK=2/2 (high), or that uses a matrix chain with change_impact HIGH or CRITICAL (high), gets a second check before SDLC_05. /pr-readiness starts a separate, read-only Devin session that did not write the code (tools/verifier.py start). It gets the acceptance criteria, the diff and the claims file, and answers pass or fail with its findings. The answer is kept in {STORY}-verifier.yaml in the session folder, and SDLC_05 needs a pass there. The Change confidence tab on the Tech Lead dashboard shows claims verified against unverified, each verifier verdict, the failed rounds before a pass, and missed impacts: files changed by the fix of a defect linked to the story in Jira that the link-graph walk from the story's own files did not predict (tools/verifier.py missed ACME-n --defect ACME-m).

The link graph and keeping it current. tools/kbgen/gen_link_graph.py builds CROSS-LAYER/ACME_LINK_GRAPH.yaml from the ontology, the cross-module matrix, the test files' imports, the commits that name a Acme Claims story and the Behave scenarios of the QA repository ACME/claims-qa (read only, from ~/repos/claims-qa or CLAIMS_QA_REPO). A scenario covers the screen whose tile its steps click and checks the tables its database steps query; when the QA repository is not on the machine, the committed scenario links are kept. Picked Behave scenarios carry run_by: QA: QA runs them in SIT, so confidence.py required lists them for QA instead of failing. python3 sdlc/framework/tools/kb_sync.py --base origin/<branch> rebuilds the matrix, the ontology, the link graph and the KB manifest in that order; /implement runs it before every PR and commits the result, and /pr-readiness runs it with --check and fails when any of them is stale. Documents that need Snowflake are reported not run and rebuilt after deployment by /kb-refresh.

Evidence, tests and data contract. tools/confidence.py checks that a change rests on evidence. /plan writes {STORY}-claims.yaml in the session folder, one claim per fact the routing map relies on, each citing a path:line, a KB file, a link-graph node or link, or a matrix chain; confidence.py claims checks each one and SDLC_04 shows how many were verified. Until the date in .devin/rules/confidence.yaml (two sprints) an unverified or missing claim only warns; after it, SDLC_04 is blocked. confidence.py tests --base origin/<branch> --pack <test pack> walks the link graph from the changed files to the tests that cover them and writes them into the test pack as selected_tests; confidence.py required --pack <test pack> fails /eval and /pr-readiness while any of them is not run or failed. confidence.py contract --base origin/<branch> checks table and column names and literal types in the changed SQL against DB-DOCS/DB_TABLE_REGISTRY.yaml and the ontology; the live Snowflake check is always reported not run. Each command prints its [SDLC] evidence, [SDLC] tests or [SDLC] contract line for Argus Trace.

Sharing the framework with another team

The framework can be handed to another team as one shared copy, with every team value (people, Jira, Confluence, repos, hosts, ids) swapped for a made-up "Acme" example. tools/build_distribution.py builds it from tools/distribution_map.yaml into sdlc/kb/v<major>.<MMDDYY>/ (the major version and the build date, for example v2.101826 for 18 October 2026) and the same folder as sdlc/kb/v<major>.<MMDDYY>.zip. Older dated folders stay as they are. The copy is not rebuilt with every PR: the tech lead rebuilds it by hand once a month (a Devin reminder goes out on the 1st), so between rebuilds --check reports it out of date. --check fails when the copy or the zip is out of date or a leak scan finds a team value; --test installs the copy into a scratch repo and runs its own checks and tests. The copy holds the skills, agents, playbooks, rules, templates, hooks, workflows, tools, Argus, the KB prompts and this manual, Argus manual and the presentations (also together in MANUALS/). It has no application code and no knowledge base: the other team builds its own with /kb-build.

The other team unzips it and runs python3 install.py --target <their repo> (in a Devin session or on a PC). It asks for their values or reads them from a file, puts the skills, agents, rules and hooks into .devin/, and runs the checks; they commit the result. Then python3 sdlc/framework/tools/register_playbooks.py lists the playbooks as !pb_<nn>_<name> macros, and with --apply and a service-user DEVIN_API_KEY creates them in Devin Cloud, or updates the ones that are already there. The Jira and Confluence secrets are added by hand in Devin Cloud. The copy's README.md has the full steps.

Defect root cause and escape

The Root cause tab on the QA and Tech Lead dashboards lists every SIT and UAT defect open or closed in the last 30 days: the story it is linked to, the stage that should have caught it (a SIT defect should have been caught by unit tests and code review, a UAT defect by SIT), the root cause, and the files its fix changed that the link graph did not predict from the story's files (the same measure as "Impacts missed" on the Change confidence tab). When someone closes a defect, Devin Cloud asks them for the root cause, one of requirement, design, code, data, environment or test gap, and puts it on the defect as a "Root cause:" comment after they say approved (tools/defect_rca.py).

Feedback on the framework

After a gate brief or an artefact, Devin Cloud asks the person who read it one line: was this useful, yes or no, and why. The answer goes into SHARED/framework-feedback.yaml after they say approved (tools/framework_feedback.py), never into Jira. The Tech Lead dashboard's Framework feedback tab shows the yes and no counts per gate brief or artefact, the least useful first, with the latest notes.

Anyone can also press Feedback on Argus top bar, next to Help. The form asks what kind it is (something went wrong, an idea, or something that worked well), what it is about, and what happened. Nothing else is typed: the Argus adds what it already knows, shown under Sent with your feedback. That is the page and ticket, the person's open and recent runs (session link, stage, status, last error and what Devin last said), the status light, the problems it noticed in the last day and its version. Send starts a short Devin run. The run adds one file under SHARED/workbench-feedback/ and raises a pull request into the working branch, then merges it straight away with no review. If Bitbucket refuses the merge, the pull request stays open.

Argus also watches itself while people use it. It writes down failed Jira, Devin Cloud or Bitbucket calls, requests the page sent and the server refused or failed, runs that ended in error or got no answer for 30 minutes, Wake pressed three times on one run, the same action started twice in a few minutes, and script errors on the page. The same problem again counts on the same line. Each line has a suggested fix (console/observer.py); one it does not recognise says needs a look. These go with the next feedback, or once a day on their own.

The group shows both: Team feedback has what people sent, each with its session details. Argus noticed has each problem with how often it happened, how many people hit it, their roles (no names), first and last seen, and how to fix it.

The same group has a Recommended changes tab: framework changes the monthly Team Insights run recommends from how the team uses Devin. Each one says what to change, why, how many sessions and people it comes from, the expected gain and the skill, command or file it touches. It starts as new; you accept, reject or mark it done with python3 sdlc/framework/tools/team_insights.py recommend decide R-001 accepted --by "<your name>" --write, and only accepted changes go to the backlog.

3. Work a ticket with Devin Cloud

  1. Start. Pick a ticket on the left and press Start SDLC, or type a new requirement in the box at the bottom left. Leave Dry run ticked to see what would happen without pushing anything. Each run is its own Devin Cloud session working in the background, and you stay on the ticket: a note confirms the start, and the ticket shows This ticket's run with a progress bar, the current stage and anything waiting for you. Argus never switches you to the session. Devin tests the story in Devin Cloud; leave Bring to local unticked. Before the PR, /implement runs the security scans: GovRAMP access-control checks, plus Checkmarx and Wiz once their access works (until then they show as not run).
  2. Follow it. Open the run on the ticket shows a progress bar, the stage rail (intake → research → plan → implement → test → release → KB refresh), the questions waiting for you at the top, Devin's messages and Open in Devin. The step-by-step lines (stage, agent, skill, gate) are not shown there; Trace has them. Replies show within seconds while the page is open.
  3. Answer its questions. When the session asks numbered questions, they appear as a form on the ticket and at the top of the run page, outside the scrolling messages. Fill it in and send it, and the session carries on. The ticket's text stays as it is. Once SDLC has started on a ticket, nothing in Argus or the run changes its description or acceptance criteria. On the ticket a run only moves its status (In Progress), adds sub-tasks, logs hours, adds comments and asks for approvals; a proposed change to the description or acceptance criteria goes on the ticket as a comment for the PO or BSA.
  4. Approve or forward a gate. When a stage needs a human decision, the gate shows under To approve on the right, with the documents to read. Approve it, send it back with reasons, or press Forward… to send it to someone else as a Jira Approval sub-task (section 7). Sub-tasks before coding. The last gate before code changes (SDLC_04, or HOTFIX_PLAN_CODE_APPROVAL for a hotfix) shows Add sub-tasks to <story> before coding starts when the run has a Jira story. Tick it to see the sub-tasks Devin suggests from the routing map (the standard DEV set until Devin has posted its suggestions). Each row has a title, an original estimate in hours and a technical description: the files and functions to change, what changes in each, the tests, and the acceptance criteria it covers. You can edit all three, add rows with + Add sub-task and remove them with ×; the total is underneath. When the story already has sub-tasks, each one shows as a row with Devin's suggested change, if any; tick Update <key> in Jira on the ones you want changed, and the rest are left as they are. When you approve, a box lists what will be created and what will be updated, with each estimate, and asks Update Jira?; nothing is written until you press Yes, update Jira. New sub-tasks are created under the story with the original estimate, the description, the AI-Used label and you as assignee; ticked ones get the new title, estimate and description. This happens before any code is changed. In a dry run Devin only lists them and writes nothing to Jira. Leave the box unticked to approve without adding sub-tasks.
  5. Wake it. A session that has gone to sleep does no harm. Answering, approving or pressing Wake starts it again from where it stopped.
  6. Archive, close or delete it. These are under More ▾ next to Refresh on the run page. Each one asks first, in a box that names what it does; Delete is in red.

4. Wrap up a ticket

Development, QA and UAT each have their own story in Jira, so "done" means done for this story. The wrap-up box appears on the test card after Return to Cloud. It never moves anything on its own.

Cloud checks nothing is left

The check starts by itself after Return to Cloud. You can also press Check everything is done. The ticket's Cloud session looks at four things: the newest evidence has 0 failed, and a reason for every not-run item; the PR exists and nothing has been pushed since the tested commit; there's no open question, unsigned gate or waiting step in the session; and which statuses the Jira ticket can move to next. It only reads during this check, so nothing changes yet.

The box then says either Ready with a short summary, or Not ready with the reason. When it's not ready, there's no Jira move on offer. Fix the reason and press the check again.

Pick the next Jira status, or leave it

Each button is one of the ticket's real Jira transitions, as Jira reported them, for example Ready for Review, Ready for Testing or Ready for Approval. Leave as is changes nothing. When you click a status, Argus asks you to confirm, and then Cloud makes exactly that one move with the team service account. The box then shows "moved to …".

12. How it works

  1. You use one browser page, served by Argus inside your own Devin Cloud session (!argus or /argus). [E: console/server.py]
  2. Argus starts runs, chats and short helper sessions, sends messages, uploads evidence and reads each session's messages. In Devin Cloud it does this through your host session: each call goes to ~/.sdlc/console/bridge/outbox, the bridge loop in that session runs it with the session's own tools, and the sessions it starts are child sessions under your name, with no API key. Every 5 seconds one search asks Devin Cloud which of your open runs changed, and those runs are read straight away, whatever their status, so a new question or gate shows within about 5–10 seconds. A run with no change is read again once a minute at most. [E: console/bridge.py, console/server.py Poller]
  3. Cloud pushes the PR branch and the test pack to Bitbucket. It's the only part that touches Jira, through the team service account. [E: console/server.py CLOUD_JIRA_TAG, TASK_REPLY_TAG]

14. Limits today

  • One APM. The ticket lists, the repo and the Jira service account are all APM0000000 (Acme Claims, Acme-Claims-Web). [E: console/server.py] [?4]
  • Jira lists are as old as the last read. A list is read once and kept until you press Refresh or Check now, because each read goes through the day's Cloud reader session and takes about a minute. [E: CLOUD_JIRA_TTL = 0]
  • PR state only. The PR panel shows open, merged or declined. It doesn't show approvals or conflicts, and each check is a short Cloud session. [E: console/server.py CLOUD_PR_TAG]
  • Cloud replies are read, not pushed. While a page is open on a session, or waiting for an answer to something you sent, Argus reads that session every few seconds. [E: WATCHED_SECONDS, REPLY_WAIT_SECONDS]
  • Backlog writes are off by default. The Backlog tab shows every change as a preview. It only writes to Jira when SDLC_BACKLOG_WRITES=1 is set and the ticket (or its epic) is in SDLC_BACKLOG_TICKETS. [E: console/backlog.py]
  • The Jira writes are new. Post to Jira, the wrap-up Jira move, and answering or deciding a sub-task were tested with Devin Cloud and Jira stubbed out. Watch the first real use of each. [A3]
  • Archive is Argus's own. Archive is a tag and a filter. The session still shows as normal on the Devin website. [E: v3 archive call returned 403]

16. Decisions behind it

Jira goes through Cloud. The PC never holds a Jira key. Reads and writes are short Cloud sessions with the team service account. That costs about a minute each time.

Bitbucket stays in charge of PRs. No Merge or Approve in Argus, so Bitbucket's approval and branch rules always apply, and the merge is recorded under the person who did it.

Nothing happens by itself. Jira moves, closing, archiving, answers and approvals are always a click and a confirm. Helper sessions are the only ones that end on their own.

Archive and Close are different. Archive hides a session but keeps it resumable. Close ends it.

One folder per ticket, one zip per run, one Cloud session per ticket. The evidence goes back to the session that wrote the code, so Cloud can check it against the PR head.

Control is passed as plain messages. Anyone can read who had the branch and when.

Ready for a sprint

Before an epic's stories go into a sprint, check the epic has:

  • two or three sentences on who benefits and what changes for them;
  • a link to the BRD or Confluence page with the detail;
  • two to six measurable business outcomes as its acceptance criteria;
  • its specialty, or Foundational;
  • dependencies on other teams named, with a contact;
  • stories for what the user sees and for performance, security and access needs;
  • open questions answered, or listed with who will answer them.

Updating the knowledge base
  1. Ask for the change in plain English, for example: Add the 2027 ProgramB program year to the risk program glossary.
  2. Devin makes the change and shows exactly what is different.
  3. Reply approved. Devin stamps the change with the approver's name and the time, and opens a pull request.
  4. A team member with merge rights merges it.
