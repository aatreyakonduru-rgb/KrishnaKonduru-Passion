Argus: how it works

One architecture, ten looks. The dots show data moving for one role at a time: developer or lead, PO/BSA/Scrum Master, approver, then tester. Pick a look, and pick a role to watch only that one.

What the picture shows

  1. Developer or lead. Starts a run on the Runs page. The server keeps the run in a small cache and writes a Devin call to the bridge outbox. The bridge loop in the host Devin Cloud session runs it with the session's own tools and creates the SDLC run session, which reads the repo rules, knowledge base and Snowflake (read only, through MCP). Its [SDLC] lines come back through the bridge inbox and turn into the stage rail and numbered questions. On a PC the same calls go straight to the Devin API with the person's key.
  2. PO, BSA or Scrum Master. Opens the backlog grid; a short Jira reader session fetches the tickets. The dashboard build session reads people.yaml and builds the dashboard for that role, with its tabs such as the sprint leave calendar, which reads the Confluence Sprint Leave page. Save on a tab sends a SDLC block to the day assistant session, and after approved it updates the roster or leave page and raises a people.yaml PR.
  3. Approver. Replies approved on the gate card. Only then does the run session write: Jira story and sub-tasks, Confluence pages, a devin/* branch and a PR into feature/devin-sdlc. The PR state session keeps the Runs page up to date, a person merges, and when Bitbucket has a newer commit the updater offers Update and restarts Argus.
  4. Tester. Presses Test on my PC. Devin Local runs the story's test pack on the PC and sends the evidence to the run session, and the result shows on the Runs page.

Notes

Every look shows the same parts and links, taken from Argus code: console/server.py, console/bridge.py, the dashboard roles in .devin/rules/dashboard-roles.yaml and the tools that keep the roster, Sprint Leave page and sprint sheets.

The dashboard tabs listed are a sample; each role sees its own set of tabs.
