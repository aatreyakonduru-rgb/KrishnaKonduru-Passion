Overview

What This System Is

The Acme Claims Agentic AI System is a knowledge base-centric SDLC automation platform that transforms requirements into production-ready code through an 8-stage pipeline with 10 human approval gates.

It operates on two levels simultaneously: a technical SDLC pipeline for developers, architects, and QA — and a plain-English business layer for Product Owners, Business Systems Analysts, and finance partners who need to gather requirements, plan sprints, and track delivery without touching code.

Three Core Principles

1. KB-Centric

All analysis, gap detection, and story generation reads from a committed knowledge base — not live source code. The KB is the single source of truth.

2. Progressive Context Loading

3-stage selective KB loading: Stage 1 (Intent Router), Stage 2 (Layer-Scoped KB), Stage 3 (On-Demand Expansion). Load only what's needed, when it's needed.

3. Human-in-the-Loop

10 mandatory approval gates across 8 SDLC stages. No gate can be bypassed. Enforced via approvals.yaml + hooks.v1.json.

KB-Centric Model

The knowledge base sits at the center of all operations:

  • KB Builder Pipeline (Pipeline 1): Generates KB artifacts from source code (one-time, then on-demand)
  • SDLC Pipeline (Pipeline 2): Reads committed KB artifacts (never queries live source during analysis)
  • Staleness Check: Auto-runs before every gap analysis to detect KB drift
  • KB Refresh: Runs after every PROD deployment to keep KB in sync
Critical Rule: The SDLC pipeline does NOT read source code during gap analysis. It reads the committed KB. If the KB is stale, the staleness check flags it and the agent falls back to source code for that layer only.

Workflow Phases

  1. Phase 1 — KB Generation: /app-run-pipeline or /db-discovery → generates KB artifacts
  2. Phase 2 — SDLC Analysis: /sdlc → reads committed KB → produces stories
  3. Phase 3 — Code Changes: Developer implements → PR includes code + KB updates
  4. Phase 4 — Post-PR Verification: /app-knowledge-refresh post-pr → verifies KB sync

Provenance Tags

Because these documents mix verified implementation with business intent, every claim carries its origin, and disagreements are left visible rather than reconciled into a single comfortable answer.

TagMeans
[SOURCE-VERIFIED]Checked against repository source; source wins over any document
[CONFLUENCE-FACT]Stated in a Confluence page or attachment, with no code to confirm or deny it
[DESIGN-INTENT]Designed and documented, but not present in the code today
[JIRA-FACT] / [JIRA-INFERRED]Read from a Jira field, versus derived from summary text or cadence
[UNRESOLVED]Cannot be settled from available sources — becomes a /document-validation question
[TL-VALIDATED]Settled by a named reviewer; may establish intent or ownership, but never overwrites a [SOURCE-VERIFIED] claim
Zero Inference Rule: Every fact in a code-derived KB artifact must be traceable to source code (file path + line number). No [INFERRED] tags are permitted in those artifacts. The externally sourced documents above are the exception by design: they may state things the code cannot, which is exactly why each claim carries a provenance tag and why anything unsettled stays [UNRESOLVED] until a reviewer answers it.
Direction of travel: Confluence and Jira → repository KB → the Devin-generated wiki. The wiki cannot be edited or fed external content — it is regenerated from the indexed branch — so the only way to improve it is to improve what the repository holds. All knowledge-base work is committed straight to feature/devin-sdlc.

Stage 1: Intent Router

Always loaded (small, required):

  • 16_REQUIREMENT_ROUTING_MAP.yaml — keyword → module/tables/layers/jobs
  • 18_DB_CROSS_MODULE_MATRIX.yaml — column-level dependency chains
  • DOMAIN_CONTEXT.md — business vocabulary

Process:

  1. Tokenize requirement text into lowercase keywords
  2. Match against triggers patterns in routing map (case-insensitive regex)
  3. Identify matching routing_entry (or entries if cross-module)
  4. Build draft affected_scope block with 12 layer flags
  5. Set specific_tables, specific_endpoints, specific_etl_scripts, downstream_jobs
  6. If no match: set confidence=LOW, fallback to full KB load

Stage 3: On-Demand Expansion

During gap analysis, the agent may discover dependencies not covered by Stage 2. The system allows up to 3 on-demand expansions:

Trigger Action
Gap analysis references a table NOT in specific_tables Load only that table's entry from DB_TABLE_REGISTRY. Log: [STAGE-3-EXPANSION: loaded {table_name}]
Gap analysis identifies a dependency chain not in specific_chains Load that chain_id from 18_DB_CROSS_MODULE_MATRIX. Log: [STAGE-3-EXPANSION: loaded chain {chain_id}]
Gap analysis identifies a downstream job not in downstream_jobs Load that job's section from 11_DB_DATA_LINEAGE. Log: [STAGE-3-EXPANSION: loaded downstream job {job_name}]
Gap analysis encounters UI→staging→review→FeedFile 3-tier flow Load db_approval_flow chain for module. Log: [STAGE-3-EXPANSION: loaded approval flow for {module}]
Staleness check flagged a Stage 2 KB artifact as STALE Fall back to source code for that layer. Log: [STAGE-3-FALLBACK: {artifact_name} stale — using source code]
An item in expansion_hints is confirmed relevant Load the specific KB section or source file. Log: [STAGE-3-EXPANSION: expanded hint '{hint_text}']

Expansion Cap Behavior

Max 3 expansions. If more than 3 on-demand expansions are needed, the system STOPS gap analysis and surfaces to the user:

"This requirement touches more layers than initially scoped. Recommend running /investigate to map all dependencies before proceeding, or re-running /intake with a broader scope statement."

Gap analysis status is set to NEEDS_SCOPE_REVIEW.

Session State: approvals.yaml

Every requirement gets its own owner-scoped session directory under agentic/context/session/{OWNER}/{REQ_ID}/. The approvals.yaml file tracks gate status:

The owner segment is the fix to a flaw in the initial design, where session state sat in one unscoped directory per requirement: two people on the same branch overwrote each other's files and a resumed session could continue somebody else's work. Owner scoping is now a rule rather than a convention (.devin/rules/session-isolation.md), requirement IDs stay globally unique across owners, cross-owner sessions are never written to, and approvals.yaml keeps owner distinct from signed_by. Gate Enforcement: hooks.v1.json

The .devin/hooks.v1.json file enforces gate sequencing at the tool level:

  • gate-phase-advance-check: Blocks research-phase commands if SDLC_01 is not approved
  • no-prod-file-mutation-check: Warns before writing to KB artifacts under docs/knowledge-base/
  • pii-guard: Blocks file writes containing PII patterns (SSN, DOB, raw member IDs)
  • no-hardcoded-secrets: Blocks file writes containing hardcoded secrets (AWS keys, passwords, API tokens)

The logic itself lives in .devin/hooks/*.sh; the JSON only points at the scripts. That is a fix, not a detail: the hooks were originally written as pwsh -Command one-liners, and PowerShell is not installed on Devin Cloud's Linux VMs, so the intake gate check, the PII block and the secrets block were all silently inert there — present in configuration and doing nothing. The same port fixed gate-phase-advance-check reading whichever approvals.yaml had most recently been touched anywhere under the session root, frequently a colleague's, and so gating your work on their approval state; it now reads your own owner directory only. The scripts deliberately fail open, so a broken hook cannot wedge every write, and an 18-case harness (.devin/hooks/tests/run-hook-tests.sh) covers them, including a regression test that another owner's pending gate does not block you.

Result: No gate can be bypassed. The system will not proceed to the next stage until the current gate is signed in approvals.yaml.

Skills are executable units of work. They are organized into four classes:

Class A: Orchestrators

Complexity Estimation

Key principle: Story points measure complexity, risk, and uncertainty — not hours. Hours are read off from points after scoring. They are never the input.

5-Dimension Scoring

Score each dimension 0, 1, or 2. Sum all five scores (max 10), then look up the Fibonacci point value.

Dimension Question Score 0 Score 1 Score 2
SCOPE How many distinct areas of the codebase does this touch? Isolated — 1 file/function, 1 layer Contained — multiple files, 1 layer or 2 tightly coupled layers Broad — 3+ files or 2+ layers with independent logic
RISK How hard is it to undo this if something goes wrong in production? Safe — fully reversible, no data loss on rollback Managed — reversible with care or a follow-up step High — data mutations, breaking changes, external system coupling
UNKNOWNS How well do we understand the full scope of this story right now? Clear — same pattern done before, spec is unambiguous Some gaps — core understood, 1–2 unclear edges Significant unknowns — approach uncertain, discovery needed
DEPENDENCY Does completing this story depend on another team, system, or approval? None — self-contained, team controls everything Internal — depends on another team or shared service within org External — third-party vendor, external API, or regulatory approval
TESTABILITY How hard is it to verify this story is correct? Straightforward — unit tests cover it Moderate — integration test or data setup required Complex — end-to-end testing, real data volume, or load testing

Special Rules

UAT Points — always 1

No exceptions, no modifiers. UAT is the PO exercising the acceptance criteria. If UAT feels complex, the ACs need more work — not more points.

SIT Points — derived from impl

impl ≤ 3 → SIT = 1  |  impl = 5 → SIT = 2  |  impl = 8 → SIT = 3  |  impl = 13 → SIT = 5. Modifiers do not apply to SIT.

needs_grooming = true

Triggered when UNKNOWNS = 2 AND at least one other dimension = 2. Do not assign story points — leave null. Run /grooming-assistant first.

needs_split = true

Triggered when base score ≥ 10 OR (base pts + modifiers) > 13. Suggest split boundaries by SCOPE dimension. Run /story-splitter.

What a Gate Interaction Must Contain

Gate presentation is defined once, normatively, in .devin/rules/gate-presentation.md, and the gate-bearing skills defer to it instead of each restating it — which is how they used to drift apart. The rule's central requirement is that the approver sees what they are signing before they choose: the gate content, the artefact paths, the approval_criteria from approval-gates.yaml and the blocks_if_failed consequence all appear in the same message as the options — Approve, Reject with reasons, or Approve with notes — rather than the approver being asked to type APPROVED against a summary they have to go and verify themselves.

  • Signatures name a person. Gate records used to read signed_by: user, a literal string with no audit value. The approver's real name and email are now taken from the message they approved with.
  • The full approval record is written. approval_record_schema had been sitting unused in approval-gates.yaml; signing now writes decision, approver_name, approver_role, rationale, artifacts_reviewed and next_gate alongside the existing status, signed_by, signed_at and notes that /resume-session and the advance-check hook read.
  • Delegation is recorded, not blocked. An approver outside a gate's named role list is accepted with a visible warning and role_mismatch: true on the record, because covering for an absent colleague is normal and an audit trail is more useful than a refusal.
  • Rejection stops the phase. A rejection leaves status unapproved, so the advance-check hook keeps the next stage blocked.
  • One source for criteria. The per-gate approval-criteria checklists that had been copied into /research, /plan and /release were deleted in favour of the canonical, more complete lists in approval-gates.yaml.

Answering Intake Questions in a Generated Form

Clarifying questions were previously answered by opening the session folder and typing into the artefact files. /intake-phase now writes its question set to {REQ_ID}-INTAKE-QUESTIONS.yaml and renders it as a single-file HTML form (tools/gen_intake_form.py) with no external assets and no network calls — so it renders in the Devin sidebar and can be forwarded as an attachment to a stakeholder who is not in the chat. Answers are held in browser local storage keyed by requirement ID, so a half-filled form survives a reload, and "Generate answers" emits a paste-back block that the intake skill saves verbatim as {REQ_ID}-INTAKE-ANSWERS.yaml for provenance, matches to questions by id, and asks the remainder in chat. A "Not applicable / unknown" answer is treated as explicitly unanswered rather than as an answer. Chat Q&A remains the default; the form is for question sets over about six, or when the answers have to come from somebody outside the session. The same pattern was later reused for /document-validation.

Future Improvements

Each item below states what the system does today and what the targeted improvement would deliver. All items are sourced from concrete gaps observed during system build.

1. Automated End-to-End (E2E) Test Generation Testing

Current
The test-gen skill generates unit tests (test_*.py) and integration tests (*.test.tsx) per story. The test-exec skill produces a TEST-REPORT.md with exact pytest / npm test commands. Devin cannot execute tests — execution is performed by the developer in SIT. UAT is always a manual 1-point story performed by the PO.
Future
Add a dedicated E2E test skill (Playwright or Cypress) that generates full-stack browser tests for UI-layer stories — covering DB write → API response → UI state in one test run. Wire test execution into a CI pipeline so results are posted back to the TEST-REPORT.md automatically, eliminating the manual developer-runs-tests step.

2. Cortex Analyst Integration Database

Current
09_DB_SEMANTIC_LAYER.yaml documents SCD2 rules, RLS policies, tenant isolation, and global filters. It is read by the KB context loader during gap analysis. SQL queries for gap analysis are hand-written by the agent based on KB context.
Future
Register 09_DB_SEMANTIC_LAYER.yaml as a Snowflake Cortex Analyst semantic model. Enable natural-language queries against live Acme Claims Snowflake data directly from the agentic system — eliminating hand-written SQL for data-heavy gap analysis and enabling ad-hoc data validation during research.

3. Automated KB Refresh on Git Push KB Builder

Current
/kb-refresh is invoked manually after PROD deployment as Stage 7 of the SDLC pipeline (SDLC_08 gate). If a deployment happens outside the agentic workflow (e.g. hotfix), the KB is not automatically updated and may drift.
Future
Trigger /kb-refresh automatically on merge to main via a Bitbucket pipeline webhook. Eliminates KB drift for any deployment path — agentic or otherwise — without requiring the team to remember the manual step.

4. Jira API Write for Story Creation Integration

Current
After SDLC_03/03a approval, the jira-backlog-exporter skill produces JIRA-BACKLOG.yaml — a structured file ready for Jira import. The team manually imports this file into Jira. The acme-jira MCP server is available for reading but Jira API write permissions have not been granted to the Devin account.
Future
Once Jira API write permission is granted, automatically create Jira epics and stories from JIRA-BACKLOG.yaml via the MCP server immediately after SDLC_03a approval — eliminating the manual import step entirely.

5. Dynamic Expansion Cap Sizing KB Context

Current
The Stage 3 on-demand expansion cap is fixed at 3 for all requirements. If more than 3 expansions are needed, gap analysis halts with NEEDS_SCOPE_REVIEW regardless of requirement complexity.
Future
Size the cap dynamically from the Stage 1 complexity signal: change_risk=LOW → cap 2, change_risk=MEDIUM → cap 3, change_risk=HIGH → cap 5. Prevents premature scope review blocks on legitimately broad high-risk requirements.

6. Automated Complexity Re-estimation Triggers SDLC

Current
Story points are estimated by the Research Agent at Stage 2 and locked after SDLC_03a (Tech Lead approval). If the Plan Agent's insertion locator finds significantly more files than anticipated, the estimate is not automatically revisited — the discrepancy is only surfaced if the developer notices it.
Future
If the insertion locator at Stage 3 finds a file count or layer count that increases the SCOPE dimension by ≥1 level versus the estimation basis, automatically flag the story for re-estimation and surface it to the Tech Lead before any code is written.

7. Confluence KB Push Post-Refresh Integration

Current
KB artifacts (YAML + MD) are committed to this repo after each refresh. Non-Devin stakeholders (POs, BSAs, architects) can only view them by navigating the repo directly. The confluence-enterprise-knowledge MCP server is available but not yet used for writes.
Future
After SDLC_08 is approved, automatically push updated Markdown KB artifacts to the team's Confluence space via the MCP server — keeping documentation visible to all stakeholders without manual copy-paste.

8. Inter-Requirement Dependency Detection & Story Sequencing SDLC

Current
Within a single requirement, stories are ordered by layer (DB-DEV → API-DEV → UI-DEV → ETL-DEV) and this ordering is enforced at the SDLC_03a gate. The BACKLOG.md schema includes a story_dependency_graph and sprint_ordering field, but these are populated only within the scope of one REQ-ID. Across two different requirements, no automated dependency detection exists — conflicts are discovered manually during sprint planning when developers notice they both touch the same tables or APIs.
Future — Design
Add a new inter-requirement-dependency-analyzer skill, owned by the Research Agent, invoked immediately after enriched-requirements-generator completes and before SDLC_03 gate. This is the correct insertion point because stories exist at this stage but the PO has not yet approved the backlog order.

Phase 1 — Early warning at Intake: When Stage 1 intent routing completes for a new requirement, compare its specific_tables, specific_endpoints, and downstream_jobs against all other in-flight sessions in agentic/context/session/. Surface a conflict notice to the BSA immediately — before any stories are generated — so scope can be adjusted before research begins.

Phase 2 — Story sequencing at Research: After stories are generated, the skill reads all in-flight BACKLOG.md files, compares shared artifacts across REQ-IDs, and produces a DEPENDENCY-MAP.md: 
cross_req_dependencies:
  - blocks: REQ-002-DB-DEV
    blocked_by: REQ-001-DB-DEV
    reason: "Both modify CL_PG_PROV_HRCHY — REQ-001 must migrate first"
    suggested_sequence: [REQ-001-DB-DEV, REQ-001-DB-SIT, REQ-002-DB-DEV]
The skill re-orders stories in BACKLOG.md and JIRA-BACKLOG.yaml to reflect cross-requirement dependencies. At SDLC_03, the PO sees a dependency-ordered backlog. At SDLC_03a, the Tech Lead reviews DEPENDENCY-MAP.md alongside ESTIMATION-AUDIT.md as part of the gate criteria.

9. Legacy Skill YAMLs as Agent Evaluation Test Cases Quality

Current
Pre-orchestrator legacy skill definitions (e.g. routing-map-generator, change-drafter, coverage-analyzer) are commented out in agent YAMLs as legacy aliases. Their inputs/outputs blocks are documented but not used.
Future
Repurpose each legacy skill's inputs/outputs block as a ground-truth regression test fixture. Run against current orchestrators to verify that the new orchestrated pipeline produces equivalent outputs to the pre-orchestrator baseline — automated quality gate for any future agent refactoring.

Shared-Branch Session Isolation — a Fixed Design Flaw

The initial design wrote session state to a single unscoped directory per requirement, context/session/{REQ_ID}/. That worked for one person, and broke as soon as two people worked the same branch: both wrote the same files, a resumed session could pick up somebody else's in-flight work, and an unscoped git add swept up a colleague's uncommitted artefacts. This is fixed, and the fix is a rule (.devin/rules/session-isolation.md) rather than a convention, so every skill inherits it.

  • Owner scoping. Session state lives at context/session/{OWNER}/{REQ_ID}/, where the owner slug is derived from git config user.email — resource3@acme.example becomes resource3. An existing session's recorded owner always wins over the derived slug, so an owner is never rewritten.
  • No accidental cross-reading. Skills read your own directory and fall back only to the legacy unscoped ones, which belong to nobody. Naming a requirement that exists under another owner shows you whose it is and asks for explicit confirmation before reading, and never writes to it — it offers to copy it into your own directory instead. Read-only reporting (/bsa-dashboard, /pi-plan, /release-notes, /sprint-review-summary) is deliberately exempt, because aggregating across owners is the point — it shows the owner beside each requirement.
  • Globally unique requirement IDs. ID allocation scans every owner's directory plus the legacy ones, so two people cannot mint the same REQ ID and Jira references stay unambiguous.
  • Committing without collateral damage. Staging is by explicit path, never git add . and never the whole context/session/ tree; git pull --rebase precedes a push, and because owner scoping means nothing overlaps inside your own directory, the rebase is clean. Commits happen at each milestone and each gate signature rather than once at the end — an ephemeral VM that ends with uncommitted artefacts loses them.
  • Owner is not approver. approvals.yaml records owner (who ran the session) separately from signed_by (who approved that gate). They are frequently different people and are not conflated.
One honest caveat: auto_commit and auto_push in .devin/config.cloud.json are declarative settings that no skill implements. Nothing commits your session state on your behalf — the staged commit is an explicit step, which is exactly why the rule requires it at every milestone.

Extending the Framework — the Contract

If you add… The rule
A skill One level deep at .devin/skills/<name>/SKILL.md, with frontmatter carrying name (matching the directory), a description, and triggers containing both user and model. Without model it can only be invoked by exact name

Known Limits — State Them Before Someone Else Finds Them

  • Static validation is not runtime proof. All 70 skills load and are wired; roughly 15 have actually been executed, across a smoke test, one end-to-end run and the BSA/PO demo.
  • Slash commands are branch-scoped. They exist only in sessions whose checkout contains them; playbook macros are org-wide. A session on the default branch will not see them.
  • Database skills need Devin Desktop for Snowflake access; they cannot run in Devin Cloud.
  • ETL documentation needs the sibling repos (claims-etl, _glue_files, _lmda_files) cloned alongside this one.
  • Resume is proven through stage 3. Re-entry after stages 4–7 is untested.
  • The dashboard under-reports when a session folder has no approvals record.
  • Coverage in the test report is estimated, not read from a coverage tool.
