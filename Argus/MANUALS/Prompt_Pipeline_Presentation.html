1. Executive Summary

Two-Pipeline Architecture

This system uses a two-pipeline architecture to automate the Acme Claims software development lifecycle with human validation gates at every critical decision point.

Pipeline Purpose When to Run
Pipeline 1: Knowledge Base Builder Generates structured documentation from source code + schema + domain knowledge Once per module; refresh after production deployments
Pipeline 2: SDLC Change Pipeline Takes a new requirement → stories → code → test → deploy Every time a new requirement arrives

Key Principles

  • ✅ Every AI-generated artifact is traceable to confirmed evidence (no hallucination)
  • ✅ Every critical decision has a human approval gate (no unsupervised deployment)
  • ✅ Machine-readable YAML artifacts enable AI agents to programmatically consume the knowledge base
  • ✅ The unified SDLC pipeline works across ALL layers (DB + API + FE + ETL) — not per-layer

8. How AI Consumes the Knowledge Base

Machine-Readable Artifacts (YAML)

These are the primary consumption targets for AI agents:

Artifact AI Use Case Key Fields
DB Semantic Layer Text-to-SQL generation Tables, joins, filters, column types
DB Data Contracts Type validation across layers DB type → API type → FE type chains
DB Entity Registry Alias resolution + code file lookup Entity → table + API model + FE component + ETL script
DB AI Guardrails SQL generation rules Mandatory filters, forbidden patterns, severity
DB Cross-Module Matrix Story generation + impact analysis Column → all consumers across layers
API Endpoint Registry API change routing Endpoint → model → serializer → SQL → table
API Data Contracts Request/response validation Input schema, output schema, validation rules
FE Component Registry Frontend change routing Route → component → API calls → state
ETL SQL Patterns ETL code generation Canonical patterns per script type
ETL Table I/O Contract ETL change impact Script → source tables → target tables → mandatory columns

SDLC_02 Selective Loading (v1.1 change)

SDLC_02 no longer loads the full KB by default. Load only the layers the requirement type touches:

  • API-only: Endpoint Registry + API Contracts + DB Guardrails + Cross-Module Matrix
  • FE-only: Component Registry + API Contracts + DB Entity Registry + DB Guardrails + Cross-Module Matrix
  • DB-change: Semantic Layer + Data Contracts + Entity Registry + DB Guardrails + Cross-Module Matrix
  • ETL: SQL Patterns + Table I/O Contract + DB Contracts + DB Guardrails + Cross-Module Matrix
  • Cross-cutting: Load ALL (last resort only)

9. End-to-End Example: New Feature

Requirement

"Add a secondary approver level for high-value contracts (>$1M PMC)"

Step 1: SDLC_01 Intake

  • AI asks: "What defines 'high-value'? Which PMC column? Does this apply to all contract types?"
  • Human answers: "CL_CNTRCT_PARM.TOTL_PMPM_AMT > 1000000. Applies to PCMH and ProgramC only."
  • Output: REQ-20260815-001-SPEC.md

Step 2: SDLC_02 Gap Analysis

AI reads full KB and identifies:

  • DB gap: No SECONDARY_APRVR_ID column exists on CL_UI_APRVR_ASGNE
  • DB gap: CL_UI_PG_STTS has no PENDAPRVR4 status code
  • API gap: No endpoint for secondary approval flow
  • FE gap: Approval UI only shows 3 levels (L1/L2/L3)
  • ETL gap: DataSync doesn't propagate approval status changes for L4
  • Output: REQ-20260815-001-GAP-ANALYSIS.md

Step 3: SDLC_03 Stories

AI generates 8 stories across 4 epics (DB first → ETL → API → FE).

Step 4: SDLC_04 Routing (per story)

For Story 1 (DB): "ALTER TABLE CL_UI_APRVR_ASGNE ADD COLUMN SECONDARY_APRVR_ID VARCHAR(50)"

  • Files to touch: Migration SQL, CL_CD_CTLG_VAL insert for PENDAPRVR4
  • Files NOT to touch: CL_PG, CL_CNTRCT_PARM (no schema change there)

Step 5: SDLC_05 Code Generation

AI reads existing migration pattern → generates conformant migration SQL.

Step 6: SDLC_06 Tests

AI generates unit tests (API), E2E tests (full flow), boundary tests (exactly $1M threshold).

Step 7: SDLC_07 Promotion

DEV → SIT → UAT → PROD with checklist at each gate.

Post-Deployment

Re-run: DB_01 → DB_10 → DB_11 → DB_15 → DB_18

10. Maintenance & Staleness Detection

Gap-Fill Protocol

Handles cases where the Knowledge Base Builder was run but left documentation gaps (files not read, sections marked [unconfirmed]).

  • Entry point: PROMPT_GAP_FILL.md
  • After gap-fill: Run SDLC_08 (Validation Log)
  • Gap-fill → SDLC drift rule: Tag affected SDLC sections [STALE — re-evaluate after GAP-FILL-{SESSION_ID}]

SESSION_MANAGER

Mandatory session handoff for multi-session AI runs. Without it, the next session starts cold and risks re-reading already-read files or missing context.

When to Run Staleness Checks

Trigger What to Check Action if Stale
Sprint start All layers Refresh stale docs before new stories
Post-Prod deploy Affected layer(s) Refresh Discovery + downstream
Monthly cadence DB schema (SD-Q1 through SD-Q6) If drift: full refresh
New team member onboard Nothing Just point them to this guide

Refresh Cascade Rules

Change Detected Minimum Re-run
New DB table DB_01 → DB_04 → DB_10 → DB_11 → DB_15 → DB_18
New DB column (contracted table) DB_01 → DB_10 → DB_11 → DB_18
New API endpoint API_01 → API_03 → API_10 → API_11
New FE component FE_01 → FE_03 → FE_12
New ETL script ETL_01 → ETL_03 → ETL_12 → ETL_13
New code value in DB DB_01 → DB_06 → DB_10 → DB_15

  • ✅ Human gates at every critical decision — no unsupervised deployment
  • ✅ Machine-readable YAML artifacts enable AI agents to consume the knowledge base programmatically
  • ✅ Unified SDLC pipeline works across ALL layers (DB + API + FE + ETL)
  • ✅ Selective KB loading in SDLC_02 (v1.1) — load only what the requirement type touches
