Tickets track. You need a colleague who knows the system, can do the work and help you make decisions. That's what we built.

Our team, Acme Claims, built an agentic AI SDLC system on Devin Cloud. It is role-aware: it knows whether you are the solution lead, an ETL developer or the QA lead, and talks to you that way. It helps before the ticket, around it as it moves, after it ships, and beyond any single ticket.

113 skills (9 public) · 38 playbooks · 15 agent roles · 10 approval gates · ~230-document knowledge base

Problems we are trying to address

the problem
  • Requirements were a two-line Jira story; the rest lived in Teams, email and hallway chats.
  • Decisions were not recorded — why something was built one way was in someone's head.
  • Learning the system meant booking a senior and reading code; onboarding took weeks.
  • Picking up someone else's work started from zero.
  • Approvals happened in chat; nobody could say who signed off on what, or when.
  • Docs, DB, ETL and Confluence drifted apart; nobody knew which one was current.
  • Test evidence was scattered across workbooks, screenshots and mails.
  • Every role asked the same questions — where are we, what breaks if I touch this — and got answers from memory.

Two pipelines, one knowledge base

Pipeline 1 builds the knowledge base from code, Snowflake, Confluence and Jira. Pipeline 2 takes a requirement through the SDLC using it. After each production deploy, /release prompts /kb-refresh to bring the KB up to date; a staleness check before every gap analysis catches drift and falls back to source.

Before the ticket: you don't need one to get started

Give a good developer a requirement and they ask a few questions, then build it. This does the same. Leads and architects decide from a question, not a Jira key — Jira tracks the work; it doesn't start it. /start knows who is typing, so a lead and an ETL developer get different first answers.

Context is bigger than a ticket

~230 documents

One knowledge base, generated from the sources, not typed by hand: the database, the modules, ETL, Confluence (about 1,109 SIT test cases), Jira and what QA's automation suite tests.

Staleness checks catch drift; 61 shared prompts rebuild it any time.

It is plain Markdown and YAML in our own repo, with the skills, rules and prompts. If we move off Devin Cloud, the knowledge and the process come with us; only the engine changes.

Ask it what you'd ask a senior

Is this idea worth a sprint? What breaks if we change this rule? How does this work? Could we commercialize or externalize it? Answers in about five minutes, with where it read them (/feasibility-check, /impact-radar, /investigate).

Or give /intake a sentence, meeting notes or a Jira key; it writes the spec, pulling in the epic, the reporter and the ticket history.

Around the ticket: gates are traffic rules

A gate doesn't judge the code; it says who decides, and when. Quality comes from the context and the checks; the gate makes sure a named person owned the call. Only the word approved opens one (/approve).

Decide it your way

Say "I approve 1, 2 and 3; send 4 to Resource 17." Resource 17 gets a Jira sub-task with the full brief; the session checks back every 15 minutes, then carries on, and everything said lands on the story (/send-approval). A gate that sits too long gets a daily nudge — nobody keeps a list. Resource 17 sees it in her Argus under Waiting on me, with a desktop pop-up, and approves, rejects or answers it there.

Training wheels

Today the person running the session can sign their own gates, and the record says so. One setting limits signing to the right role. The wheels come off as we get comfortable.

The PR brings its own proof

Tests go in the real test files. A drifted knowledge base is fixed in the same PR, or /pr-readiness fails it. No chasing docs afterwards.

Sourced, not guessed

Every fact in a spec, gap analysis or plan is tagged: read from a source, an agreed assumption, or not known yet — with who can answer. If it doesn't know, it asks instead of guessing, and a reviewer can check every tag against its source.

one page per role

What's waiting on me, what I asked, and what's sat more than three days. Approve, reject or pass it on from the page.

When to use it: first thing in the morning, or whenever you want to know what needs you. It's a report; nothing runs until you click.

/argus ↗

where the work happens

Pick a story off the board and watch it go through intake, research, plan, code and PR. Answer questions and sign gates in one place.

When to use it: to do the work: start a story, run a menu item (Investigate, Document validation…), answer Devin's questions, sign a gate, or close a finished session.

Test on my PC

Cloud → PC → Cloud

Cloud writes the code and the PR. One click in Argus on your laptop checks out the PR; Devin Local runs the checks and walks you through each acceptance criterion in the browser. Return to Cloud sends one evidence zip, tied to the commit, to the same session. Cloud checks it, offers the ticket's next Jira status, and you continue, archive or close the session.

When to use it: when a PR is ready to test. Developers, QA and UAT share the screen; Post to Jira puts the evidence on the ticket.

Walkthrough (5 min 35 s, screen only)

Intake → research → plan → verification → code diffs → PR handoff. The last frame shows the branch and PR link; the Bitbucket page needs the corporate network.

1 · Intake

  • Knew who was asking and in which role, from the roster.
  • Took a sentence and the requester's answers; wrote a spec first, code later.
  • Every line tagged: read from a source, agreed, or not known yet.
  • Nothing invented to fill the page.

Intake sign-off: "approved"

2 · Research

  • Started in the knowledge base, not the code: which layers, where each lives.
  • Staleness check — KB pages compared with the code before planning on them.
  • Read only the files on that path: a dozen out of thousands.
  • Learned how the feature works today and the pattern it follows.
  • Sized from the complexity matrix; wrote down what it could not confirm.

Gap analysis and backlog sign-off: "approved"

3 · Plan

  • Routing map: each file, the exact spot in it, and the order — DB, API, UI, tests.
  • Names the pattern to copy from the code next door, and what not to touch.
  • A lead sees the shape of the change before a line is written.

Routing map sign-off: "approved"

4 · Implement

  • Code written to the map, in our style, with the repo's rules read first.
  • Tenant filters, bound parameters, no PII, no new endpoints — checked, not assumed.
  • A test per acceptance criterion; the ones this box could run, ran.
  • Self-checked against rules and spec; KB fixed in the same change.
  • Said plainly what it could not prove here. The PR carries all of it.
