Acme Claims AI Documentation — Enhancement Recommendations

Analysis of Prompts, Outputs, and Domain Context in light of new UI Process Documentation  |  August 2025

What was reviewed: All prompt files in Prompts/Acme Claims-API-FE/, Acme Claims-SHARED/, Acme Claims-DB/, Acme Claims-ETL-PIPELINE/; all output files in Outputs/Acme Claims-FE/; the shared DOMAIN_CONTEXT.md; and Answers_Required/ logs.

Key finding: The new UI Process Documentation has dramatically enriched the knowledge base around the user experience layer (exact field names, screen flows, error messages, validation rules, conditional logic). However, this knowledge is only partially absorbed into the prompts and outputs. Six high-impact and seven medium-impact gaps are identified below with specific file-level fixes.

1. Domain Context (DOMAIN_CONTEXT.md) — What to Add

This is the single most leveraged file — it is injected into every session. Enriching it here propagates automatically to all downstream prompts and outputs.

HIGH §16 is incomplete — Provider Group workflow is missing screen-level detail

Prompts/Acme Claims-SHARED/DOMAIN_CONTEXT.md · §16

The GUI workflow section (§16) covers Contract Configuration in detail (all 3 steppers, field types, validation rules) but has almost no equivalent for the Provider Group workflow. The PG workflow steps listed in §3 are high-level only. The new UI Process documentation should allow you to add:

  • Exact PG creation screen fields (PG Name, LOB association, TIN/NPI entry, Remit Info tabs)
  • Bulk Upload vs. Inline entry paths
  • Dashboard tabs: Summary, TIN/NPI, Remittance, Attribution + "Days Left to Refresh"
  • Lock indicator behaviour — when another user is editing a PG, the lock overlay fires
  • PG approval states: Draft → Pending Approval → Under Review → Approved / Rejected (and corresponding My Queue sections)
  • Rollback action — confirmed from source code; document when it applies

Action: Add a new subsection "§16b — Provider Group GUI Workflow" mirroring the structure of §16.

HIGH UI Interaction Patterns not documented as reusable rules

Prompts/Acme Claims-SHARED/DOMAIN_CONTEXT.md · §16

§16 documents Pentagon icon and multi-value popups only in the context of Contract steppers. But these UI patterns are used across PG screens, Definitions screens, and Template screens too. Prompts that generate FRDs and User Manuals need to know to apply these rules everywhere, not just in contracts. Create a reusable §16c — Universal UI Interaction Patterns:

PatternTriggerBehaviour
X iconAny fieldClears/removes the value
Pentagon icon (⬠)Complex nested fieldsOpens "Dependent Data" popup; Add Row = new entry; applies for Affinity, TennCare fields, Quality Bonus, CC Fee, Target Trend, and equivalent PG fields
Allow Multiple ValuesMulti-value fieldsOpens "Enter Values for [Section]" popup → Add New
Save and NextStepper navigationSaves current stepper; toast: "Success - Data Saved Successfully for Screen: [name]"
Save and ReleaseCollaborative editingMoves to Global queue — accessible from other users' Draft section
Review and Submit AllSubmissionMoves to Under Review state
Filter icon (My Queue)Global filterSearch by Contract ID or PG ID before taking action

MEDIUM Definitions and Templates navigation sub-sections not documented

Prompts/Acme Claims-SHARED/DOMAIN_CONTEXT.md · §16 UI Navigation Structure

The navigation tree in §16 ends with Definitions and Templates as placeholders. The new UI docs should reveal what Definitions contains (benefit packages, employer groups, specialty groups, etc.) and what Templates covers (pre-built contract templates by type). Add these as sub-bullets so prompts generating the User Manual know to document them.

MEDIUM Missing: Dashboard screen documented (counts by status, drill-down)

Prompts/Acme Claims-SHARED/DOMAIN_CONTEXT.md · §16

The 07_UI_SPECIFICATION.md output references Dashboard Cards showing counts per status, but this is not in the domain context. Both the Contract Dashboard and PG Dashboard status count cards should be documented as authoritative UI facts (status labels, what clicking a card does, what the grid shows). This lets PROMPT_5 (User Manual) produce accurate dashboard documentation without guessing.

2. Prompts — Specific Enhancements per Prompt File

HIGH PROMPT_5_USER_MANUAL.md — Too generic; outputs prove it

Prompts/Acme Claims-API-FE/PROMPT_5_USER_MANUAL.md

The current output (Outputs/Acme Claims-FE/04_USER_MANUAL.md) is extremely thin — it describes Contract Configuration in 8 generic bullet points with no field names, no dropdown values, no error messages, no conditional logic. Compare this to the authoritative detail in §16 of the domain context. The prompt is not directing the AI to use §16.

Add to PROMPT_5:

  • An explicit instruction: "For Contract Configuration screens, use Domain Context §16 as the authoritative field list. Do not summarise — reproduce every field name, dropdown option, conditional, and validation rule from §16 in procedural (How-To) format."
  • A matching instruction for PG screens once §16b is added to the domain context.
  • An explicit list of screen sections the User Manual must cover: My Queue (Draft / Under Review / Pending for Approval tabs), Contract Dashboard, PG Dashboard, Definitions, Templates, Assign Approvers, Request Rerun.
  • A [SCREENSHOT NEEDED] placeholder rule for exact UI labels that cannot be inferred from code — currently this rule exists but is not applied consistently.

HIGH PROMPT_6_PROCESS_DOCUMENTATION.md — Needs "UI field → FeedFile column" traceability section

Prompts/Acme Claims-API-FE/PROMPT_6_PROCESS_DOCUMENTATION.md

The process documentation prompt covers swim lanes well, but the outputs lack a critical artefact now that UI field knowledge is rich: a UI Screen → Snowflake FeedFile Column mapping. Each business process step should identify which UI fields write to which FeedFile table columns via DataSync. The domain context already has §13 (Contract Field Vocabulary) and §6 (FeedFile table catalogue). The prompt should require:

  • A new section in each process: "Data Written to Snowflake" — maps each UI field captured in that process step to the target FeedFile column.
  • Example: "Contract Name (UI) → CNTRCT_NM in CL_CNTRCT_PARM via DataSync".

This is the most valuable cross-reference document for the DB team and downstream consumers, and with the current knowledge base it is fully derivable without new stakeholder input.

HIGH PROMPT_3_FUNCTIONAL_REQUIREMENTS.md — Conditional logic rules not being captured

Prompts/Acme Claims-API-FE/PROMPT_3_FUNCTIONAL_REQUIREMENTS.md

The FRD output (02_FUNCTIONAL_REQUIREMENTS.md) is missing all conditional business rules that are now documented in §16 of the domain context. These are real functional requirements:

  • If Contract Type = Musculoskeletal or ProgramB → Contract Sub Type becomes mandatory (51 options)
  • If Pre Trigger Duration is entered → Pre Trigger Duration Units becomes mandatory
  • Pentagon popup toggling (Yes/No reveals dependent data form rows)
  • Approver Level 1 ≠ Approver Level 2 — system enforces this
  • Comments on Approve/Reject: max 250 characters

Add to PROMPT_3: A "Conditional Mandatory Fields" section requirement. Instruct the AI to extract all conditional rules from §16 of the domain context as formal FR statements in the format: "The system SHALL make [Field X] mandatory when [Field Y] = [Value Z]."

MEDIUM PROMPT_7_DIAGRAMS.md — Missing "UI Screen → API Endpoint → FeedFile Table" data flow diagram

Prompts/Acme Claims-API-FE/PROMPT_7_DIAGRAMS.md

The diagrams prompt produces good architecture and C4 diagrams but doesn't produce the most useful operational diagram now that UI knowledge is complete: a data flow diagram that traces from each UI screen through the API endpoint to the Snowflake table. Add a new mandatory diagram type:

  • "Diagram 5 — UI-to-Data Flow per Business Entity"
  • Separate flows for: Contract (Stepper 1/2/3 → DataSync → CL_CNTRCT_* tables), Provider Group (PG creation → DataSync → CL_PG* tables), Run Request (Rerun UI → CL_RUN_RQST → DPDF job trigger)
  • Use the confirmed DPDF Job IDs from §7 of domain context

Prompts/Acme Claims-API-FE/PROMPT_2_BUSINESS_REQUIREMENTS.md

The BRD output lacks a comprehensive role-to-screen access matrix. The domain context now has §9 (RBAC roles) and §16 (navigation/workflow), which together can produce an authoritative matrix. Add a required output section:

MEDIUM ETL and DB prompts — Add UI-originated data context

Prompts/Acme Claims-ETL-PIPELINE/ · Prompts/Acme Claims-DB/

The ETL and DB prompt pipelines are documented from the data/pipeline perspective but do not reference which UI actions originate the data they process. Now that the UI layer is fully documented, each ETL and DB prompt should load Outputs/Acme Claims-FE/05_PROCESS_DOCUMENTATION.md as an optional prerequisite so the ETL/DB AI can say: "This DataSync SQL executes when the user clicks Save and Next on Stepper 1 of Contract Configuration." This closes the documentation gap between layers.

3. Output Documents — Specific Gaps to Re-generate

HIGH 04_USER_MANUAL.md — Needs full regeneration

Outputs/Acme Claims-FE/04_USER_MANUAL.md

The current document is structurally thin — it describes Contract Configuration in 8 generic bullets and Provider Group in 7. With §16 now in the domain context and the enhanced PROMPT_5 described above, a full regeneration should produce:

  • Step-by-step walkthrough of all 3 Contract steppers with every field, every dropdown option, every conditional rule
  • Provider Group creation walkthrough (Inline and Bulk Upload paths)
  • My Queue navigation: Draft / Under Review / Pending for Approval tabs, Filter icon usage, Save and Release vs. Review and Submit
  • Approver workflow: how to assign approvers, L1/L2 validation rule, approve/reject with comment
  • Dashboard: how to read status count cards and drill into the grid
  • Request Rerun: when to use it, what it does
  • Glossary sidebar at first use of every acronym (PMC, SSAV, LOB, PSL, etc.)

Priority: Regenerate after updating PROMPT_5 and §16b of domain context.

HIGH 05_PROCESS_DOCUMENTATION.md — Process 1 (PG Lifecycle) is missing detail

Outputs/Acme Claims-FE/05_PROCESS_DOCUMENTATION.md

The current output for Process 1 is structurally correct but has placeholder SLOs ([from discovery]) and sparse swim lane steps. With new UI knowledge, the gaps that can be filled immediately are:

  • Exact My Queue tabs for PG: Draft / Pending Approval / Under Review / Approved / Rejected
  • Lock indicator — when the lock overlay shows and what the user must do (wait or contact the editing user)
  • Days Left to Refresh in the Attribution tab — what it means operationally
  • Rollback action — when it is available and what it reverts
  • Daily email SLA (5 business days) with audit note that escalation is stated but not automated

MEDIUM 02_FUNCTIONAL_REQUIREMENTS.md — Grid column definitions incomplete

Outputs/Acme Claims-FE/02_FUNCTIONAL_REQUIREMENTS.md

Grid column definitions are partially started (TIN/NPI substitution grid is documented) but the Contract Dashboard grid and PG Dashboard grid column lists carry [REQUIRES STAKEHOLDER INPUT] flags. The 07_UI_SPECIFICATION.md file already has the confirmed column references from PGDashboardConfig.tsx. These should be cross-linked and the FRD updated — no new stakeholder input needed, just cross-reference the 07_UI_SPECIFICATION.md evidence.

MEDIUM 07_UI_SPECIFICATION.md — Incomplete after A3 (Contract Module)

Outputs/Acme Claims-FE/07_UI_SPECIFICATION.md

The document has good detail for the application shell and starts on A2 (PG Module) and A3 (Contract Module) but the Definitions screens, Templates screens, Request Rerun screen, and Admin screens (Assign Approvers) are not documented. These are all confirmed to exist from §16 navigation structure in the domain context. They should be added as new sections A4–A7.

LOW FE_SERVICES_DOCUMENTATION.md — Add business context column

Outputs/Acme Claims-FE/FE_SERVICES_DOCUMENTATION.md

The services documentation is thorough at the TypeScript interface level but each service function lacks a "Business Context" column mapping it to a UI screen + user action. Example: getProviderGroupList() → "Called on PG Dashboard load; populates the AG Grid on the My Queue page." This makes the document useful to BSAs and new developers, not just TypeScript engineers.

4. New Prompt / Output to Create

NEW PROMPT_13_UI_TO_DATA_FIELD_MAPPING.md

Prompts/Acme Claims-API-FE/ (new file)

This is the highest-value new artefact the current knowledge base can produce. It would generate a single cross-cutting reference document mapping every UI field visible to the user → the backend API parameter → the Snowflake column it writes → the FeedFile table it lands in via DataSync. No equivalent currently exists and it directly answers the question "what does clicking Save actually do to the database?"

Output: Outputs/Acme Claims-FE/13_UI_FIELD_TO_DATA_MAPPING.md

Prerequisite inputs: Domain Context §13 + §16 (UI fields), 07_UI_SPECIFICATION.md (confirmed screen elements), Outputs/Acme Claims-DB/07_DB_SCHEMA_CATALOG.md (column definitions), ETL DataSync SQL docs.

NEW PROMPT_14_VALIDATION_RULES_CATALOGUE.md

Prompts/Acme Claims-API-FE/ (new file)

The new UI Process documentation contains a rich set of validation rules that are spread across §16 of the domain context (field types, conditional mandatories, character limits, numeric-only rules, dropdown constraints). These should be consolidated into a single testable catalogue used by QA, BSAs, and the test generation prompt (SDLC_PROMPT_F). Format: FR ID | Screen | Field | Rule Type | Rule Description | Error Message.

Output: Outputs/Acme Claims-FE/14_VALIDATION_RULES_CATALOGUE.md

NEW 08_CHANGE_IMPACT_MATRIX.md for Acme Claims-FE

Outputs/Acme Claims-FE/ (new file — DB module already has this)

The DB output folder already has 04_DB_CHANGE_IMPACT_MATRIX.md. The FE module lacks an equivalent. Now that the UI layer is fully mapped (screens → services → API endpoints → Snowflake tables), a change impact matrix can be produced: for any given UI screen or feature, what other screens/services/FeedFile tables are affected if it changes? This is critical for sprint planning and change routing (SDLC_PROMPT_D).
