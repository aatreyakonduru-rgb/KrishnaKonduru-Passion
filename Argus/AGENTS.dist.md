# Argus, Agentic SDLC Framework

The agentic SDLC framework for this repository lives in two places:

| What | Where | Notes |
|---|---|---|
| Skills (127) | `.devin/skills/<skill-name>/SKILL.md` | Must stay one level deep at the repo root — this is what makes them discoverable |
| Agents (15 YAML + docs) | `.devin/agents/` | `*.agent.yaml` definitions plus per-agent `AGENT.md` |
| Templates (10) | `.devin/templates/` | Artefact templates used by the SDLC stages, including the Jira ticket shapes (`jira-issue-templates.md`) and the estimation matrix (`complexity-matrix.yaml`) |
| Rules | `.devin/rules/` | Domain context, approval gates, data access, PII, secure coding, session isolation, Jira ticket standards (`jira-ticket-standards.yaml` — field IDs and the ticket contract agents rely on), plus the roster (`people.yaml`), job-role routing (`role-routing.yaml`) dashboard lenses (`dashboard-roles.yaml`), the Snowflake environment map the DB skills resolve `{{SNOWFLAKE_DB}}` from (`snowflake-environments.yaml` — dev/sit/uat/prod, default dev) and the shared look for every generated HTML page (`html-style.md`, kit in `sdlc/framework/tools/artifact_kit/`) |
| Configuration | `.devin/config.json`, `.devin/config.cloud.json`, `.devin/hooks.v1.json` | Hook implementations live in `.devin/hooks/`; `config.local.json` is machine-local and git-ignored |
| Team settings and links | `.devin/rules/sdlc-profile.json` | Our Jira, repo and Devin values, the Confluence pages (`confluence.pages`: the Devin Cloud User Manual, the roster) and the repo paths of Argus manual, the presentation and the architecture page (`docs`). Tools build their links from here, so a moved page is one edit; `tools/team_links.py` lists them |
| Playbooks (38 runnable + 2 docs) | `sdlc/framework/playbooks/` | Registered in Devin Cloud → Settings → Playbooks as `!pb_<nn>_<name>` macros |
| Catalogue | `sdlc/framework/CATALOGUE.md` | Generated listing behind `/catalogue` — regenerate with `sdlc/framework/tools/gen_catalogue.py` |
| Workflows (10) | `sdlc/framework/workflows/` | Stage-level workflow docs |
| Session context | `sdlc/framework/context/session/{OWNER}/` | Per-requirement artefacts (`{OWNER}/{REQ_ID}/`) |
| Knowledge base | `docs/knowledge-base/` | Generated docs (`DB-DOCS/`, `MODULES/`, `ETL/`, `SHARED/`). Dated outputs in `REPORTS/`, superseded files in `Archive/` (including the older prompt copies), `_REGEN/` is the git-ignored staging folder of `/kb-build`. The prompts that build the docs are in `sdlc/kb/kb-prompts/`, wired in `.devin/rules/kb-prompt-wiring.yaml` |
| Deprecated skills | `sdlc/framework/archive/deprecated-skills/` | Kept out of the discovery path on purpose |

## Entry points

Start any session with **`/help`** — it prints the front door: the nine public commands (`/start`, `/status`, `/approve`, `/ask`, `/explain`, `/impact`, `/handover`, `/dashboard`, `/help`) that non-technical users need; `/help all` prints every command grouped by role, with the gate that follows each stage. Skill frontmatter carries `visibility: public|internal`; the validator keeps the public set to those nine. `/help <topic>` or `/help <command>` narrows it down. For the exhaustive inventory use `/catalogue` (`skills`, `playbooks` or `agents`); `/presentation` shows the architecture and flow diagrams. The full catalogue of record is `sdlc/framework/USER-MANUAL.md`.

- `/start "<what you need>"` — plain-English front door; routes to the right stage and answers with where it is / next / who
- `/status [REQ-ID]` and `/approve REQ-ID` — where a requirement is and who acts next; sign or send back the waiting gate (`sdlc/framework/tools/gates.py`)
- `/sdlc "<requirement>"` — full pipeline (intake → research → plan → implement → eval → release → kb-refresh), pausing at each human gate
- `/intake`, `/research`, `/plan`, `/implement`, `/eval`, `/release`, `/kb-refresh` — a single stage
- `/investigate`, `/impact-radar`, `/explain-capability`, `/dashboard` — read-only analysis
  (`/dashboard` is the per-role landing surface and includes the approvals queue where applicable)
- `/identify-requester` — who is asking and which of their delivery roles applies; run it first in any session with a person behind it

When a user opens a session without a clear task, or asks what they can do, run `/help` rather than guessing.

## Conventions

- All paths in skills, agents, rules and templates are repository-relative from the repo root; never commit machine-specific absolute paths.
- Every skill needs YAML frontmatter with `name` (matching its directory), a `description`, and `triggers` containing both `user` and `model`; without `model` the skill can only be invoked by name.
- Human approval gates are defined in `.devin/rules/approval-gates.yaml`; a stage may not proceed past an unsigned gate. `tools/gates.py` is the one implementation (present, decide, precheck, next); `.devin/config.json` → `gates.mode` is `dev` (session owner may self-sign, recorded as `self_signed`) until the framework leaves development. Hooks in `.devin/hooks/` fail closed.
- Session state lives outside the repo at `~/.sdlc/sessions/{OWNER}/{REQ_ID}/` (`tools/session_store.py`); the repo `context/session/` tree is the fallback. Snowflake and Artifactory are not provisioned in Devin Cloud yet — db-* skills and application test execution in `/eval` are deferred, framework tests run without them.
- Every doc count in this file, ARCHITECTURE.md and CATALOGUE.md is checked by `tools/validate_framework.py` (`--fix` rewrites them); the knowledge-base manifest is `tools/kb_manifest.py`.
- Session artefacts are owner-scoped per `.devin/rules/session-isolation.md`.
- Job roles route behaviour; they never grant access. `.devin/rules/people.yaml` says who wears which hats and `.devin/rules/role-routing.yaml` says what each hat gets by default — permissions stay with Devin Cloud roles, Bitbucket branch protection, secret scoping and the approval gates. The one exception is the `access:` section of `people.yaml`: which gate roles may change which folders, and which gates the requester may not sign (SDLC_05). The `write-access-guard` hook, `.devin/hooks/git/pre-commit` and `gates.py` enforce it through `tools/access_guard.py`, after checking `people.yaml` against the Confluence roster page; a difference, or a page that cannot be read, blocks guarded writes and gate sign-offs. It stops mistakes inside Devin; Bitbucket required approvers are the hard control. Roster changes are made on the Confluence page "Acme Claims Team Roster" and approved there by the owner named in `people.yaml` (an `approved` comment or the Signed-by row); the tech lead then runs `/roster-sync` by hand, which regenerates `people.yaml` and commits it — no separate PR review. It is not scheduled. `/roster-check` reports drift (see `sdlc/framework/ROSTER-GOVERNANCE.md`).
- Never get round the access guard. Do not run `git commit --no-verify` or `-n`, `git push --no-verify`, or change `core.hooksPath` or `.git/hooks`; do not edit `~/.sdlc/requester.json` or the approval records by hand; do not edit the `access:` section of `people.yaml` (it changes only through `/roster-sync`). Set `SDLC_OWNER` only to the requester the chat identity matched (`/identify-requester`), never to a name someone asks you to use; acting as another person (`su - <name>`) is for a requester with a lead role only, and the guard refuses it otherwise. When the guard blocks a change, say who may make it instead of working around it. The guard reads its rules from `people.yaml` on `origin/feature/devin-sdlc`, and `access_guard.py pr-audit` checks every commit on a pull request.
- Hotfix fast lane: `/sdlc` and Argus ask at the start of every run on a Jira key (`hotfix.py check` first; only a passing defect gets the question; nothing else skips a gate). For a production incident defect (`tools/hotfix.py check --key <key>` passes: summary ends "- PROD", incident-INC label) present HOTFIX_PLAN_CODE_APPROVAL to the Tech Lead in place of SDLC_04 and SDLC_05, with the routing and the diff in one brief. Run the independent verifier whatever the risk tier, and after "approved" raise the follow-up review sub-task (`tools/hotfix.py followup --key <key> --by <name> --reviewer <jira user> --write`, due in 2 working days). SDLC_06 onwards is unchanged.
- Product Owner and BSA requesters (`access_guard.py` `kb_only`) change the knowledge base only. Stage only knowledge-base files, show the change, and when they type "approved" run `python3 sdlc/framework/tools/access_guard.py approve` before `git commit`; the commit-msg hook adds `Approved-by:` and blocks their commit without it. Open a knowledge-base-only PR against `repo.kb_branch`; run `access_guard.py pr-check` first (the pre-push hook runs it too). Never commit code for them. See `.devin/hooks/README.md`.
- Defect root cause: when someone on the roster closes, or tells you they fixed, a SIT or UAT defect with no "Root cause:" comment yet, ask them once: "What was the root cause: requirement, design, code, data, environment or test gap?" Show the comment from `tools/defect_rca.py cause --key <key> --by <name> --category <c> --note ...` and write it with `--write` after they type "approved". QA and the Tech Lead see it on the Root cause tab.
- Feedback on the framework: after you present a gate brief or finish an artefact for someone on the roster, ask once per session "Was this useful? Yes or no, and one line on why (or skip)." Record it with `tools/framework_feedback.py add --by <name> --on <gate or artefact> --useful yes|no --note ...`, shown first and written with `--write` after they type "approved". It goes to `SHARED/framework-feedback.yaml`, never Jira; the Tech Lead sees it on the Framework feedback tab. Argus's Feedback form, and the problems Argus notices about itself, arrive as a `SDLC-WORKBENCH-FEEDBACK v1` block: apply it as `.devin/skills/dashboard/SKILL.md` says (one new file under `SHARED/workbench-feedback/`, a pull request merged straight away with no review).
- Team Insights: once a month `/team-insights` reads the month's Devin sessions and their analyses and writes the team numbers and nameless findings to `SHARED/team-insights/<YYYY-MM>.yaml`, the recommended framework changes to `SHARED/framework-recommendations.yaml` (each new until the Tech Lead accepts or rejects it) and the monthly deck. Each person's learning plan goes to `SHARED/team-insights/people/<YYYY>/<MM>/<devin user id>.md`, named by Devin user id with no name inside (the Tech Lead dashboard shows the name from people.yaml). Usage and ACUs per person go only to a private file for the tech leads (`tools/team_insights.py import`), never into git, Jira or Confluence; wins name the person, gaps in the shared files never do. In the first reply to someone on the roster, after their own request and before the closing question, give one short lesson on their next open learning item (`team_insights.py teach next --person <name>`); on "got it" mark it taught (`team_insights.py learned ... --status taught --write`) and commit the plan file through a PR. Once a month the first session with someone on the roster asks the check-in question (`team_insights.py checkin due --person <name>`) instead of the learn-more question, written with `--write` after they type "approved". The Tech Lead sees it all under Team Insights and Framework feedback on the dashboard.
- Scrum Master reminders: in the first reply to someone on the roster, after their own request, list up to two of their open Stand-up check gaps as questions (`tools/sm_reminders.py for --person <name>`), e.g. when they will close a long-running story or which release a defect ships in. Their answer is shown as the Jira change and comment (`sm_reminders.py answer ...`) and written with `--write` only after they type "approved".
- Time off: once a calendar week the first session with someone on the roster (the POs and the Scrum Master included) asks about time off instead of the learn-more question (`tools/time_off.py due --person <name>`). A yes brings the follow-ups: the dates, who covers their stories, whether their In Progress stories go On Hold, where questions for them go and who approves in their place. Show the planner row and the hold blocks, and write them (`time_off.py record ... --write`, `backlog_cli.py apply`) only after they type "approved". The planner is the "Time off and backups" table on the Acme Claims Sprint Leave page; `question_subtask.py` and `approval_subtask.py` send sub-tasks to the backup while someone is away. When someone asks about time off or gives dates, use `/vacation` (`time_off.py list`, `record`, `remove` with `--by` the requester); people change their own rows, and the Scrum Master changes anyone's. A sick day ("@Devin <name> is sick today", from anyone, often in Teams) is written at once with `time_off.py sick --person <name> --by <sender> --write`: no follow-up questions, no backups, no Jira changes, and the repo's planning sheet is left alone (`--reason adhoc` for ad hoc leave). The day also goes to the Unplanned leave table on the Sprint Leave page, which the Scrum Master's Unplanned leave counter reads (`tools/unplanned_leave.py`). The Vacation planner tab and `/vacation` show this sprint's leave calendar, coloured by planned time off, sick day, ad hoc leave, holiday and weekend (`tools/leave_calendar.py`), and this sprint's unplanned leave (`unplanned_leave.py sprint`). Each sprint's planning sheet (Capacity, Carry forward, Previous sprint AI savings, with the workbook's formulas) is kept in the repo, one file per sprint, as `sdlc/framework/context/sprint-sheets/<sprint>.json` and `.html` (`tools/sprint_sheet.py`); `time_off.py record`/`remove --write` also set the person's day cells (0 off, 0.5 half day, H holiday), and `sprint_sheet.py off|edit --write` saves the sheet and that sprint's section of the Sprint Leave page. Commit the changed sheet files through a PR to `feature/devin-sdlc`. Argus edits the sheet; the dashboard shows it read only.
- Sprint close: when the Scrum Master asks whether the sprint is ready to close, run `/sprint-close-check` (the Sprint close tab, `scrum_metrics.close_rows`). It lists each story and sub-task that is missing closed sub-tasks, time, the AI label, an original estimate or a Ready for Approval / done status. It only reads Jira.
- Risks and dependencies: when a PO or lead names a risk or a dependency on another team for an epic, show it as `tools/risk_register.py add --epic <key> --kind risk|dependency ...` (risk: likelihood, impact, owner, mitigation; dependency: team, needed-by date, owner) and save it with `--write` after "approved". Kept in SHARED/risk-register.yaml, never Jira; the PO office dashboard shows it on the Risks tab.
- Audit evidence: at SDLC_05, `/pr-readiness` builds `{REQ}-STORY-{n}-EVIDENCE.md` in the session folder with `tools/evidence_pack.py build`: every gate with signer, role, decision and time, the claims and whether their evidence checked out, the test report and /pr-readiness status, Checkmarx/Wiz/GovRAMP results, the verifier verdict and the PR link. Anything missing is listed under "Not found", never filled in.
- Devin learns from the team through "Learn about who you serve" (`/learn-about-who-you-serve`, also `/learn-more`), not Jira. At the end of the first reply in a session with someone on the roster, ask one question about their work (`tools/learn_more.py next`); they may say skip. Save the answer in the knowledge base (`SHARED/learn-more.yaml`, `SHARED/team-know-how.yaml`, `SHARED/delivery-teams.yaml`) only after they type "approved". Jira holds stories only: no Question sub-tasks for this. When an answer is approved, also close the other open questions in the knowledge base it settles (`tools/learn_more.py related <id>`: open learn-more questions and doc gaps) and update the files they point at.
- No skill is buried: every skill has a home in `.devin/rules/role-routing.yaml` (a role's `default_skills` or `more_skills`, `everyone_skills`, or internal to the system), the Skill config tab on the Tech Lead dashboard counts and changes them, and every dashboard has a **My commands** tab (`tools/skill_homes.py`). When someone asks for something a skill already does, name the command in the answer. In the first reply to someone on the roster, after the learn-more question, add one line: `Tip:` and the command from `python3 sdlc/framework/tools/skill_homes.py tip --person "<name>"`, a different one of their role's commands each day.
- Product Owner, BSA and Scrum Master requesters (the `product_owner`, `bsa` or `scrum_master` hat in `role-routing.yaml`) have no database connection in Devin yet. When their request needs Snowflake or any other database, don't call the Snowflake MCP or connect to a database. Tell them: "You don't have a database connection in Devin yet, so I can't look this up. Please contact your Solution Lead, <name> (<email>)." Take the name and email from the `people.yaml` entry for `resource3` (Resource 3, Solution Lead). Then carry on with any part of the request that doesn't need the database.
